1. Why APIs Are Needed — Life Before APIs

1.1 Life Before APIs

Before standardized APIs, applications that needed to share data used tightly coupled, fragile approaches — direct database access from multiple applications, file-based exports (CSV/FTP transfers run nightly), or proprietary binary protocols understood only by the two specific systems involved. Every integration was custom, one-off, and brittle.

1.2 Real Problems This Caused

Old ApproachReal Problem
Direct database access between systemsAny schema change in one system silently broke every other system reading that table directly
Nightly file exports (CSV/FTP)Data was always stale by up to 24 hours; no real-time updates possible
Screen-scraping (parsing another app's HTML/UI)Extremely fragile — any UI change broke the integration instantly
Custom point-to-point protocolsEvery new integration required custom code understood by only two teams, not reusable

1.3 What APIs Actually Solve

Before vs After APIs
System A directly queries System B's database tables
— vs —
System A calls System B's well-defined API — System B's internal database can change freely without breaking System A
  • Decoupling — the consumer only depends on a stable contract (the API), not internal implementation details.
  • Real-time access — data is fetched live, not from yesterday's export file.
  • Reusability — one well-designed API can serve a web app, a mobile app, and third-party partners simultaneously.
  • Security boundary — the API controls exactly what's exposed, instead of granting broad direct database access.
  • Language/platform independence — a Java backend can serve a React frontend, an iOS app, and a partner's Python script, all through the same HTTP-based API.
Interview one-liner: "APIs exist to let independently built, independently deployed systems communicate through a stable, well-defined contract — without needing to know or depend on each other's internal implementation."

2. What Is an API? Simple Explanation with Real-World Analogy

2.1 The Restaurant Analogy

Think of a restaurant: you (the client) don't walk into the kitchen (the server/database) to cook your own food. You give your order to a waiter (the API) using a menu (the API contract) — the waiter takes your request to the kitchen, and brings back exactly what you asked for, in a standard format, without you ever needing to know how the kitchen actually works.

2.2 Formal Definition

An API (Application Programming Interface) is a defined set of rules and endpoints that allows one piece of software to request services or data from another, specifying exactly what requests look like and what responses to expect — without exposing internal implementation details.

3. SOAP — What It Is and Why REST Replaced It (Mostly)

3.1 What Is SOAP?

SOAP (Simple Object Access Protocol) is an older, strict, XML-based messaging protocol for web services, popular in the early-to-mid 2000s enterprise world — every request and response is an XML document following a formal envelope structure, and every service publishes a WSDL (Web Services Description Language) file formally describing every available operation.

3.2 A Real SOAP Request/Response

<soap:Envelope xmlns:soap="http://schemas.xmlsoap.org/soap/envelope/">
  <soap:Body>
    <GetAccountBalance xmlns="http://bank.com/services">
      <accountId>1001</accountId>
    </GetAccountBalance>
  </soap:Body>
</soap:Envelope>

<!-- Response -->
<soap:Envelope xmlns:soap="http://schemas.xmlsoap.org/soap/envelope/">
  <soap:Body>
    <GetAccountBalanceResponse>
      <balance>4500.00</balance>
      <status>ACTIVE</status>
    </GetAccountBalanceResponse>
  </soap:Body>
</soap:Envelope>

3.3 SOAP vs REST — Why the Industry Moved to REST

Real scenario: "Our Loans Service still integrates with one legacy credit bureau system that only exposes a SOAP endpoint from the early 2000s — we wrap it in a small internal adapter service that exposes a clean REST API to the rest of our microservices, so the SOAP complexity is isolated in one place instead of spreading across the codebase."

5. REST Principles Explained Simply

5.1 What REST Actually Means

REST (Representational State Transfer) is an architectural style (not a strict protocol like SOAP) built around the idea that everything is a resource (a noun, like "account" or "order"), identified by a URL, manipulated using standard HTTP verbs, with each request being self-contained (stateless).

5.2 The Six REST Constraints

ConstraintMeaning
Client-ServerFrontend and backend are separate, independently evolvable concerns
StatelessnessEvery request contains all information needed to process it — the server holds no client session state between requests
CacheabilityResponses explicitly indicate whether they can be cached, to improve performance
Uniform InterfaceConsistent resource naming, standard HTTP verbs, standard status codes across the whole API
Layered SystemClient doesn't need to know if it's talking directly to the server or through a gateway/proxy/load balancer
Code on Demand (optional)Rarely used — server can optionally send executable code (e.g., JavaScript) to the client

5.3 REST vs RESTful — Is There a Difference?

"REST" refers to the architectural style/constraints themselves; "RESTful" is the common term for an API that actually follows those constraints properly. In practice, most real-world "REST APIs" are RESTful to varying degrees — few implement HATEOAS (Section 12) fully, for example, but still call themselves RESTful.

6. Resource-Based URL Design

6.1 Think in Nouns, Not Verbs

A very common mistake: designing URLs like actions/RPC calls (/getAccount, /createOrder, /deleteCard) instead of resources. REST URLs should represent things (nouns), and the HTTP method itself represents the action.
Bad (RPC-style)Good (Resource-based REST)
GET /getAccountById?id=1001GET /accounts/1001
POST /createNewAccountPOST /accounts
POST /deleteAccount?id=1001DELETE /accounts/1001
GET /getAllCardsForAccount?accountId=1001GET /accounts/1001/cards

6.2 Real URL Design for the Banking Example

GET    /api/v1/accounts                 # list accounts
GET    /api/v1/accounts/1001             # get one account
POST   /api/v1/accounts                  # create a new account
PUT    /api/v1/accounts/1001             # full update
PATCH  /api/v1/accounts/1001             # partial update
DELETE /api/v1/accounts/1001             # close/delete account
GET    /api/v1/accounts/1001/transactions # nested resource — transactions belonging to this account
GET    /api/v1/accounts/1001/cards/8890  # deeply nested resource

6.3 URL Design Rules of Thumb

  • Use plural nouns (/accounts, not /account) — consistent across the whole API.
  • Use lowercase, hyphen-separated words for multi-word resources (/loan-applications, not /loanApplications).
  • Nest resources only 1-2 levels deep — beyond that, consider flattening with query parameters instead.
  • Never put verbs in the URL path — the HTTP method is the verb.

7.1 Real Spring Boot Controller Using All Five

@RestController
@RequestMapping("/api/v1/accounts")
public class AccountsController {

    @GetMapping
    public List<AccountDto> getAllAccounts() { ... }

    @GetMapping("/{id}")
    public AccountDto getAccount(@PathVariable Long id) { ... }

    @PostMapping
    public ResponseEntity<AccountDto> createAccount(@Valid @RequestBody CreateAccountRequest request) {
        AccountDto created = accountsService.create(request);
        return ResponseEntity.status(HttpStatus.CREATED).body(created);
    }

    @PutMapping("/{id}")
    public AccountDto updateAccount(@PathVariable Long id, @Valid @RequestBody AccountDto fullUpdate) { ... }

    @PatchMapping("/{id}")
    public AccountDto patchAccount(@PathVariable Long id, @RequestBody Map<String, Object> updates) { ... }

    @DeleteMapping("/{id}")
    public ResponseEntity<Void> closeAccount(@PathVariable Long id) {
        accountsService.close(id);
        return ResponseEntity.noContent().build();
    }
}
Interview tip: PUT is idempotent because sending the same full replacement twice results in the same final state; POST is not idempotent because calling it twice typically creates two separate resources — this distinction is a very common interview question.

9. Request & Response Design and the DTO Pattern

9.1 Why Not Expose Database Entities Directly?

Returning your JPA @Entity classes directly as API responses tightly couples your database schema to your public API contract — a database column rename breaks every client instantly, and you risk accidentally exposing sensitive fields (password hashes, internal flags) that were never meant to be public.

9.2 The DTO (Data Transfer Object) Pattern

Entity vs DTO — Separation of Concerns
Database Table (account)
→
@Entity Account (internal, JPA-managed)
→ mapped to →
AccountDto (public API contract)
@Entity
public class Account {
    @Id private Long id;
    private BigDecimal balance;
    private String internalRiskScore;   // internal only — should NEVER be exposed via API
    private String passwordHash;         // definitely never exposed
}

// Public-facing DTO — only what the client actually needs
public record AccountDto(Long id, BigDecimal balance, String status) {}

@Service
public class AccountMapper {
    public AccountDto toDto(Account entity) {
        return new AccountDto(entity.getId(), entity.getBalance(), entity.getStatus());
    }
}

9.3 Request DTOs (Separate From Response DTOs)

// Separate request DTO — doesn't include server-generated fields like id/createdDate
public record CreateAccountRequest(
    @NotBlank String customerName,
    @NotNull @Positive BigDecimal initialDeposit
) {}
Using separate Request and Response DTOs (instead of one shared class) keeps validation rules clean and prevents clients from ever being able to set server-controlled fields like id, createdDate, or status directly in a create/update request.

10. API Versioning Strategies

10.1 Why Versioning Is Necessary

Once mobile apps, partner integrations, and other services depend on your API's exact shape, you can't just change it — versioning lets you evolve the API while existing consumers keep working on the old version until they can migrate.

10.2 Versioning Strategies Compared

StrategyExamplePros/Cons
URI Path Versioning/api/v1/accounts, /api/v2/accountsMost common, visible/discoverable, simple to test; "pollutes" the URL conceptually
Header VersioningAccept: application/vnd.bank.v2+jsonClean URLs, but less discoverable, harder to test manually via browser
Query Parameter Versioning/accounts?version=2Simple but easy to misuse/forget, less strict

10.3 Real Practice — Running Two Versions in Parallel

@RestController
@RequestMapping("/api/v1/accounts")
public class AccountsControllerV1 { ... }   // old shape, existing mobile app version still uses this

@RestController
@RequestMapping("/api/v2/accounts")
public class AccountsControllerV2 { ... }   // new shape with additional fields, new mobile app version uses this
Real scenario: "We added a required riskCategory field to the account response. Instead of breaking the current mobile app release, we shipped it only in v2, migrated the mobile team over a few sprints, then deprecated v1 with a 6-month sunset notice via a Deprecation response header before finally removing it."

11. Pagination, Sorting & Filtering

11.1 Why Pagination Is Mandatory for Collections

Returning all 2 million transaction records in one response would crash the client, waste bandwidth, and slow the database to a crawl — any endpoint returning a list must support pagination from day one, not as an afterthought.

11.2 Real Spring Boot Pagination

@GetMapping("/accounts/{id}/transactions")
public Page<TransactionDto> getTransactions(
        @PathVariable Long id,
        @RequestParam(defaultValue = "0") int page,
        @RequestParam(defaultValue = "20") int size,
        @RequestParam(defaultValue = "transactionDate,desc") String sort) {

    Pageable pageable = PageRequest.of(page, size, Sort.by(parseSort(sort)));
    return transactionRepository.findByAccountId(id, pageable).map(mapper::toDto);
}

12. HATEOAS — Basic Understanding

12.1 What HATEOAS Means

HATEOAS (Hypermedia As The Engine Of Application State) is the idea that an API response should include links describing what actions/related resources are available next — so the client doesn't need to hardcode URL structures, it just follows links the server provides, similar to how a human browses a website by clicking links.

12.2 Real Example Response With HATEOAS Links

{
  "accountId": 1001,
  "balance": 4500.00,
  "status": "ACTIVE",
  "_links": {
    "self": { "href": "/api/v1/accounts/1001" },
    "transactions": { "href": "/api/v1/accounts/1001/transactions" },
    "close": { "href": "/api/v1/accounts/1001", "method": "DELETE" }
  }
}

12.3 Spring HATEOAS — Real Code

@GetMapping("/{id}")
public EntityModel<AccountDto> getAccount(@PathVariable Long id) {
    AccountDto account = accountsService.findById(id);
    return EntityModel.of(account,
        linkTo(methodOn(AccountsController.class).getAccount(id)).withSelfRel(),
        linkTo(methodOn(AccountsController.class).getTransactions(id)).withRel("transactions"));
}

12.4 Reality Check — How Often Is HATEOAS Actually Used?

In practice, most real-world REST APIs (including most internal microservices APIs) skip full HATEOAS — it adds complexity that many teams find isn't worth the benefit for APIs consumed by a frontend team that already knows the URL structure from documentation. It's more commonly seen in public APIs designed for long-term evolution by unknown third-party consumers, and is a good interview topic to understand conceptually even if you don't implement it everywhere.

13. Idempotency in REST APIs

13.1 Recap — What Idempotency Means

An operation is idempotent if calling it multiple times produces the same result/end-state as calling it once — critical because network retries and client double-clicks are a normal, expected occurrence, not an edge case.

13.2 Idempotency by HTTP Method (Built-In)

MethodIdempotent by Design?Why
GETYesJust reads data, no side effects
PUTYesReplaces the full resource with the same given state every time
DELETEYesDeleting an already-deleted resource still results in "it's gone"
POSTNo (by default)Typically creates a new resource each time — calling twice creates two resources

13.3 Making POST Idempotent — Idempotency Key Pattern

@PostMapping("/payments")
public ResponseEntity<PaymentResponse> makePayment(
        @RequestHeader("Idempotency-Key") String idempotencyKey,
        @RequestBody PaymentRequest request) {

    Optional<Payment> existing = paymentRepository.findByIdempotencyKey(idempotencyKey);
    if (existing.isPresent()) {
        return ResponseEntity.ok(toResponse(existing.get()));   // return the SAME result, don't double-charge
    }
    Payment result = paymentService.process(request, idempotencyKey);
    return ResponseEntity.status(HttpStatus.CREATED).body(toResponse(result));
}
Real scenario: "A customer's mobile app timed out waiting for a payment response and auto-retried the exact same request. Because our payment API required an Idempotency-Key header (generated once client-side per logical payment attempt), the second request was recognized as a duplicate and returned the original result instead of charging the customer twice."

14.1 Consistent Error Response Shape

Every error response across the entire API should follow the same JSON shape, so clients can write one generic error-handling routine instead of parsing different formats per endpoint.

14.2 Global Exception Handler — Real Spring Boot Code

@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(AccountNotFoundException.class)
    public ResponseEntity<ErrorResponse> handleNotFound(AccountNotFoundException ex, HttpServletRequest req) {
        ErrorResponse error = ErrorResponse.of(HttpStatus.NOT_FOUND, ex.getMessage(), req.getRequestURI());
        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(error);
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ErrorResponse> handleValidation(MethodArgumentNotValidException ex, HttpServletRequest req) {
        String message = ex.getBindingResult().getFieldErrors().stream()
                .map(f -> f.getField() + ": " + f.getDefaultMessage())
                .collect(Collectors.joining(", "));
        return ResponseEntity.badRequest().body(ErrorResponse.of(HttpStatus.BAD_REQUEST, message, req.getRequestURI()));
    }

    @ExceptionHandler(Exception.class)
    public ResponseEntity<ErrorResponse> handleGeneric(Exception ex, HttpServletRequest req) {
        log.error("Unhandled exception", ex);   // always log the full stack trace server-side
        ErrorResponse error = ErrorResponse.of(HttpStatus.INTERNAL_SERVER_ERROR,
                "An unexpected error occurred", req.getRequestURI());   // never leak internal details to the client
        return ResponseEntity.internalServerError().body(error);
    }
}
Security note: Never return raw exception messages or stack traces to the client for unexpected (500-level) errors — this can leak internal implementation details, file paths, or even SQL fragments useful to an attacker. Always log full details server-side and return a generic, safe message to the client.

15. Request Validation (Bean Validation)

15.1 Why Validate at the API Boundary

Validating input the moment it enters your system prevents bad data from ever reaching your business logic or database — fail fast, with a clear 400 Bad Request, rather than a confusing downstream error (or worse, silently corrupted data).

15.2 Real Bean Validation Annotations

public record CreateAccountRequest(
    @NotBlank(message = "Customer name is required")
    String customerName,

    @NotNull @Positive(message = "Initial deposit must be greater than zero")
    BigDecimal initialDeposit,

    @Email(message = "Invalid email format")
    String email,

    @Pattern(regexp = "^[0-9]{10}$", message = "Phone number must be 10 digits")
    String phoneNumber
) {}

@PostMapping
public ResponseEntity<AccountDto> createAccount(@Valid @RequestBody CreateAccountRequest request) {
    // @Valid triggers validation BEFORE this method body even runs — invalid requests never reach here
    return ResponseEntity.status(HttpStatus.CREATED).body(accountsService.create(request));
}

15.3 Custom Validators (Real Example — Business Rule Validation)

@Target(ElementType.FIELD)
@Retention(RetentionPolicy.RUNTIME)
@Constraint(validatedBy = ValidAccountTypeValidator.class)
public @interface ValidAccountType {
    String message() default "Invalid account type";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}

public class ValidAccountTypeValidator implements ConstraintValidator<ValidAccountType, String> {
    private static final Set<String> VALID_TYPES = Set.of("SAVINGS", "CURRENT", "SALARY");
    @Override
    public boolean isValid(String value, ConstraintValidatorContext context) {
        return VALID_TYPES.contains(value);
    }
}

16. OpenAPI / Swagger Deep Dive

16.1 What Is OpenAPI and What Is Swagger?

OpenAPI is the formal specification (a YAML/JSON document describing every endpoint, request/response shape, and auth requirement of an API). Swagger is the toolset built around that specification — Swagger UI (interactive documentation browser), Swagger Codegen (generates client SDKs), and springdoc-openapi (auto-generates the spec from your Spring Boot annotations).

16.2 Why Swagger/OpenAPI Matters So Much in Real Organizations

  • Living, always-accurate documentation — generated directly from the actual code/annotations, so it can't drift out of sync like a manually maintained Word doc.
  • Interactive testing — Swagger UI lets any developer (or QA, or a partner team) try real API calls directly from the browser, no Postman collection needed.
  • Client SDK generation — automatically generate typed client code for React/TypeScript, other Java services, or mobile apps directly from the spec.
  • Contract-first development — teams can agree on the OpenAPI spec before either side writes implementation code (Section 38).

        return accountsService.findById(id);
    }
}

17. Rate Limiting for APIs

17.1 Why Rate Limit an API

Protects backend services from being overwhelmed — whether from a buggy client stuck in a retry loop, a genuine traffic spike, or a malicious/abusive client — and ensures fair usage across all consumers of a shared API.

17.2 Real Bucket4j-Based Rate Limiting in Spring Boot

@Component
public class RateLimitFilter extends OncePerRequestFilter {
    private final Map<String, Bucket> buckets = new ConcurrentHashMap<>();

    private Bucket newBucket() {
        Bandwidth limit = Bandwidth.classic(100, Refill.greedy(100, Duration.ofMinutes(1)));
        return Bucket.builder().addLimit(limit).build();
    }

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        String apiKey = req.getHeader("X-API-Key");
        Bucket bucket = buckets.computeIfAbsent(apiKey, k -> newBucket());
        if (bucket.tryConsume(1)) {
            chain.doFilter(req, res);
        } else {
            res.setStatus(429);
            res.getWriter().write("{\"error\":\"Rate limit exceeded, try again later\"}");
        }
    }
}

20. CORS Explained

20.1 What CORS Is and Why It Exists

CORS (Cross-Origin Resource Sharing) is a browser security mechanism that blocks a web page from calling an API hosted on a different origin (domain/port/protocol) unless that API explicitly allows it — this is a browser-enforced rule, not a server-side security feature (Postman/curl/mobile apps are never blocked by CORS).

20.2 Real CORS Error (What Developers See)

// Browser console error when CORS isn't configured
Access to fetch at 'https://api.mybank.com/accounts' from origin 'https://app.mybank.com'
has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present

20.3 Real Spring Boot CORS Configuration

@Configuration
public class CorsConfig {
    @Bean
    public WebMvcConfigurer corsConfigurer() {
        return new WebMvcConfigurer() {
            @Override
            public void addCorsMappings(CorsRegistry registry) {
                registry.addMapping("/api/**")
                    .allowedOrigins("https://app.mybank.com")     // never use "*" with credentials in production
                    .allowedMethods("GET", "POST", "PUT", "PATCH", "DELETE")
                    .allowedHeaders("Authorization", "Content-Type")
                    .allowCredentials(true)
                    .maxAge(3600);
            }
        };
    }
}
Common mistake: Setting allowedOrigins("*") alongside allowCredentials(true) — browsers explicitly reject this combination for security reasons; you must specify exact allowed origins when credentials (cookies/auth headers) are involved.

25. Correlation ID & Trace ID Propagation

Full conceptual detail is covered in the Observability & Monitoring guide (Section 9) — this section focuses on the API-specific implementation: every API must accept an incoming X-Correlation-Id/traceparent header if present, generate one if absent, include it in every log line, and propagate it to every downstream call it makes.
@Component
public class CorrelationIdFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        String correlationId = Optional.ofNullable(req.getHeader("X-Correlation-Id"))
                .orElse(UUID.randomUUID().toString());
        MDC.put("correlationId", correlationId);
        res.setHeader("X-Correlation-Id", correlationId);   // echo back so the client can also log/report it
        try { chain.doFilter(req, res); } finally { MDC.clear(); }
    }
}

32. GraphQL Resolvers, Data Fetching, the N+1 Problem & DataLoader

32.1 What Is a Resolver?

A resolver is a function that knows how to fetch the data for one specific field in the schema — when a client requests account { cards { last4Digits } }, one resolver fetches the account, and a separate resolver fetches the cards for that account.

32.2 The N+1 Problem — A Real Trap

If a client queries a list of 50 accounts, each including their cards, a naive implementation runs 1 query for the accounts, then 50 separate queries (one per account) to fetch each account's cards — 51 total queries instead of 2, an easy-to-miss but serious performance trap unique to GraphQL's field-by-field resolution model.
N+1 Problem Visualized
1 query: fetch 50 accounts
↓ then, naively, PER account:
50 separate queries: fetch cards for account #1, #2, #3 ... #50

32.3 DataLoader — The Solution

DataLoader batches and deduplicates data-fetching calls within a single request tick — instead of firing 50 individual "fetch cards for account X" calls, it collects all 50 account IDs and fires one batched "fetch cards for these 50 account IDs" call.
@Bean
public DataLoader<Long, List<Card>> cardsDataLoader(CardsServiceClient cardsClient) {
    return DataLoader.newMappedDataLoader(accountIds ->
        CompletableFuture.supplyAsync(() -> cardsClient.getCardsForAccounts(accountIds))  // ONE batched call
    );
}

@SchemaMapping(typeName = "Account", field = "cards")
public CompletableFuture<List<Card>> cards(Account account, DataLoader<Long, List<Card>> cardsLoader) {
    return cardsLoader.load(account.getId());   // batched automatically behind the scenes
}
Interview tip: The N+1 problem isn't unique to GraphQL (it also happens with JPA lazy loading in REST APIs — Section 43), but GraphQL's flexible, nested query model makes it much easier to accidentally trigger at scale, which is exactly why DataLoader is considered a near-mandatory pattern in any real GraphQL implementation.

33. GraphQL Security, Query Complexity, Pagination & Federation

33.1 GraphQL Security Concerns

Because GraphQL exposes one flexible endpoint, a malicious or careless client can construct extremely deep, nested, or expensive queries (e.g., account → cards → transactions → account → cards → ... nested many levels) that overload the server — a risk REST's fixed-endpoint model doesn't share in the same way.

33.2 Query Complexity / Depth Limiting

# Real protections applied at the GraphQL server level:
# - Max query depth limit (e.g., reject queries nested more than 6 levels deep)
# - Query cost analysis (assign a "cost" per field, reject queries exceeding a total budget)
# - Timeouts per query execution
# - Persisted queries (only pre-approved, whitelisted queries allowed in production)

33.3 Pagination in GraphQL — Cursor-Based (Relay-Style)

type Query {
  transactions(first: Int, after: String): TransactionConnection!
}

type TransactionConnection {
  edges: [TransactionEdge!]!
  pageInfo: PageInfo!
}

type PageInfo {
  hasNextPage: Boolean!
  endCursor: String
}
Cursor-based pagination (rather than simple page numbers) is preferred in GraphQL because it handles data that changes between page requests more gracefully (no skipped/duplicated items when new records are inserted mid-pagination).

33.4 Error Handling in GraphQL

Unlike REST, GraphQL almost always returns HTTP 200 even for application-level errors — errors are reported inside a dedicated errors array in the response body alongside any partially successful data, which is a notable and frequently-asked interview difference from REST.
{
  "data": { "account": null },
  "errors": [ { "message": "Account not found", "path": ["account"], "extensions": { "code": "NOT_FOUND" } } ]
}

33.5 GraphQL Federation

Federation lets multiple teams each own a piece of one unified GraphQL schema — Accounts team owns the Account type, Cards team owns the Card type (with a reference back to Account) — and a Gateway composes them into a single graph, mirroring microservice ownership boundaries without forcing one team to own the entire schema.

35. gRPC — Protocol Buffers & Service Definitions

35.1 What Is gRPC?

gRPC is a high-performance RPC (Remote Procedure Call) framework from Google using Protocol Buffers (a compact binary serialization format) over HTTP/2 — significantly faster and smaller over the wire than JSON/REST, with a strongly-typed contract shared between client and server.

35.2 Protocol Buffers (.proto) — Real Definition

syntax = "proto3";

package bank.loans;

service LoansService {
  rpc GetLoanDetails (LoanRequest) returns (LoanResponse);
  rpc StreamRepaymentSchedule (LoanRequest) returns (stream RepaymentEntry);
}

message LoanRequest {
  int64 loanId = 1;
}

message LoanResponse {
  int64 loanId = 1;
  double outstandingAmount = 2;
  string status = 3;
}

message RepaymentEntry {
  int32 installmentNumber = 1;
  double amount = 2;
  string dueDate = 3;
}
Every field has an explicit number (e.g., = 1, = 2) — these numbers, not the field names, are what's actually encoded on the wire, making Protobuf messages extremely compact compared to JSON's repeated text field names.

35.3 Stub Generation

The .proto file is compiled (via protoc) into strongly-typed client "stub" and server "skeleton" code in your target language (Java, Python, Go, etc.) — both sides share the exact same generated contract, eliminating manual JSON parsing/serialization entirely and catching contract mismatches at compile time, not runtime.

37.5 Error Handling in gRPC

gRPC uses standardized status codes (distinct from HTTP status codes) — e.g., NOT_FOUND, UNAUTHENTICATED, DEADLINE_EXCEEDED, UNAVAILABLE — returned alongside an optional descriptive message, giving clients a consistent, language-agnostic way to handle failures programmatically.

45. APIs and Databases — DTO vs Entity, Avoiding the N+1 Query Problem

45.1 Recap — Never Return Entities Directly (Section 9)

Always map @Entity classes to DTOs before returning them from an API — this is worth repeating specifically in the database context because JPA's lazy-loaded relationships can also cause serialization errors or accidentally expose internal fields if entities leak directly into a JSON response.

45.2 The REST/JPA N+1 Problem (Not Just a GraphQL Issue)

// Naive endpoint — looks innocent, hides an N+1 problem
@GetMapping
public List<AccountDto> getAllAccounts() {
    List<Account> accounts = accountRepository.findAll();   // 1 query
    return accounts.stream()
        .map(a -> new AccountDto(a.getId(), a.getBalance(), a.getCards().size()))  // a.getCards() triggers a SEPARATE query PER account!
        .toList();
}

// Fixed — fetch accounts AND their cards in one query using a JOIN FETCH
@Query("SELECT a FROM Account a LEFT JOIN FETCH a.cards")
List<Account> findAllWithCards();
Interview tip: Always enable Hibernate's SQL logging (spring.jpa.show-sql=true) in development and actually look at the query count for list endpoints — the N+1 problem is easy to introduce accidentally and easy to miss until it causes real production slowness under load.

45.3 Database Design Considerations Driven by the API

  • Add indexes on columns used in common API filter/sort parameters (Section 11) — an unindexed sort column on a large table is a common real-world slow-API root cause.
  • Use database-level pagination (LIMIT/OFFSET or keyset pagination) — never fetch everything into memory and paginate in application code.
  • Keep transaction boundaries tight around the service layer method, not spanning the entire HTTP request lifecycle.

50. Interview Questions & Answers (Basic → Advanced → Scenario Based)

Q1. What is an API and why do we need it?
An API is a defined contract letting one piece of software request data/services from another without knowing its internal implementation. It's needed to decouple systems, enable real-time integration (vs stale file exports), enforce security boundaries, and let one backend serve many different consumers (web, mobile, partners) consistently.
Q2. What's the difference between REST and SOAP?
SOAP is a strict, XML-only protocol with a formal WSDL contract and built-in enterprise standards (WS-Security); REST is a lighter architectural style, usually JSON, built around HTTP verbs and resources, with more flexible/optional contracts (OpenAPI) — REST is far more common today due to its simplicity and performance.
Q3. Explain the difference between PUT and PATCH.
PUT replaces the entire resource with the given representation and is idempotent. PATCH applies a partial update to specific fields only, and isn't guaranteed idempotent depending on implementation (e.g., "increment balance by 10" applied twice produces a different result each time).
Q4. Why shouldn't you return JPA entities directly from a REST controller?
It tightly couples your public API contract to your internal database schema, risks exposing sensitive/internal fields, and can cause serialization issues with lazy-loaded relationships. Always map entities to dedicated DTOs designed specifically for the API contract.
Q5. What is idempotency and how do you achieve it for a POST endpoint?
Idempotency means repeating an operation produces the same result as doing it once. POST isn't idempotent by default; you achieve it using an Idempotency-Key header — the server checks if that key was already processed and returns the original result instead of repeating the side effect (e.g., preventing duplicate payments).
Q6. What is the purpose of Swagger/OpenAPI, and how do you implement it in Spring Boot?
OpenAPI is the specification format describing an API's endpoints/schemas; Swagger is the tooling built around it (interactive UI, codegen). In Spring Boot, adding springdoc-openapi auto-generates the spec and an interactive Swagger UI directly from your controller annotations, keeping documentation always in sync with the actual code.
Q7. How would you handle a breaking API change without disrupting existing consumers?
Introduce a new API version (e.g., /api/v2/) with the breaking change, keep the old version running in parallel, communicate a deprecation timeline via Deprecation/Sunset headers and documentation, migrate consumers gradually, then retire the old version once no traffic remains.
Q8. What is the N+1 problem, and how do you fix it in a REST API backed by JPA?
It's when fetching a list triggers one query for the list plus one additional query per item for a related entity (e.g., fetching each account's cards separately) — N+1 total queries instead of a couple. Fixed using JOIN FETCH queries, entity graphs, or batch fetching to retrieve related data in far fewer queries.
Q9. Difference between JWT and OAuth2?
JWT is a token format (a signed, self-contained set of claims). OAuth2 is an authorization framework defining how tokens (often JWTs) are issued, scoped, and used across different grant types (Authorization Code, Client Credentials, etc.) — you can use JWTs without OAuth2 and OAuth2 with non-JWT opaque tokens.
Q10. What is CORS and why does it only affect browsers?
CORS (Cross-Origin Resource Sharing) is a browser-enforced security mechanism blocking web pages from calling APIs on different origins unless explicitly allowed via response headers. It's enforced by the browser itself, so non-browser clients (Postman, curl, mobile apps, server-to-server calls) are never affected by CORS.
Q11. What's the difference between GraphQL and REST?
REST exposes multiple fixed-shape endpoints per resource, risking over/under-fetching; GraphQL exposes one flexible endpoint where the client specifies exactly the fields it needs, aggregating multiple sources in one request — at the cost of harder HTTP caching and needing careful query complexity limiting.
Q12. What is the N+1 problem in GraphQL and how is it solved?
Resolving a list of parent objects and then a related field per item (e.g., cards per account) naively triggers one data-fetch call per item. DataLoader solves this by batching and deduplicating those calls within a single request tick into one bulk fetch instead of many individual ones.
Q13. When would you choose gRPC over REST?
For high-throughput, low-latency internal service-to-service calls where the performance/payload-size benefits of binary Protobuf over HTTP/2 clearly outweigh REST's simplicity — e.g., a fraud-scoring service called on every transaction, or use cases needing native bidirectional streaming.
Q14. What is Contract-First / API-First development, and why use it?
Designing and agreeing on the API contract (OpenAPI/Protobuf/GraphQL schema) before writing implementation code, so frontend, backend, and other consumer teams can work in parallel against the agreed contract (frontend against a generated mock), reducing integration surprises later.
Q15. What are Consumer-Driven Contracts and what problem do they solve?
Each API consumer defines the exact expectations it depends on as an automated "contract" (e.g., via Pact); the provider's CI pipeline runs these as tests, catching any accidental breaking change before it's deployed — solving the real problem of a well-intentioned change silently breaking a consumer in production.
Q16. How do you secure service-to-service API calls versus user-facing API calls?
User-facing calls typically use the Authorization Code (+PKCE) OAuth2 grant tied to an actual logged-in user's identity and roles. Service-to-service calls typically use the Client Credentials grant — a machine identity with its own scopes, no end user involved — validated the same way at the resource server via JWT/OAuth2.
Q17. How would you design an API to support a long-running operation like a loan risk assessment?
Return 202 Accepted immediately with a status URL the client can poll, or accept a callback/webhook URL to notify the client asynchronously when processing completes — avoiding holding an HTTP connection open for a slow operation.
Q18. How do you handle a slow or unreliable third-party API dependency?
Wrap every call in a timeout, retry (only if safe/idempotent), circuit breaker, and fallback; isolate it with an anti-corruption layer/adapter so its quirks don't leak into your domain model; and monitor its health separately from your own service's health so incidents are correctly attributed.
Q19. What real API-related production issue have you resolved, and how?
Example: a list endpoint became progressively slower as data grew, traced to Hibernate's lazy-loading triggering an N+1 query pattern (visible after enabling SQL logging) — fixed with a JOIN FETCH query, reducing query count from hundreds to one and cutting p95 latency dramatically.
Q20. How do you ensure API documentation stays accurate over time?
Generate it directly from code using springdoc-openapi/Swagger annotations rather than maintaining a separate manual document — since it's generated from the same source as the implementation, it can't silently drift out of sync, and it's reviewed as part of normal code review on every pull request.
Q21. Why does an API work fine in Postman but fail with a CORS error from the React app?
Postman is not a browser, so it never enforces CORS — only real browsers apply the CORS check on JavaScript-initiated requests. A failure only in the browser almost always points to a missing/incorrect Access-Control-Allow-Origin configuration on the backend, not a problem with the API logic itself.
Q22. What status code should you return for a validation error, and what should the response body contain?
400 Bad Request, with a structured body listing each invalid field and a clear message (e.g., {"errors": [{"field": "email", "message": "must be a valid email"}]}) — generic, unstructured error text forces the frontend to guess which field to highlight.
Q23. How would you design an API endpoint to avoid becoming a bottleneck behind an API Gateway with a strict timeout?
Ensure the endpoint's own processing time is comfortably under the Gateway's configured timeout by optimizing slow queries/dependencies, and for genuinely long operations, switch to an asynchronous pattern (202 Accepted + status polling or a callback/webhook) instead of holding the connection open.
Q24. What's the risk of using different date/number formats across microservices, and how do you prevent it?
Inconsistent formats force every consumer to write custom, error-prone parsing per service, and subtle timezone/precision bugs slip through easily. Prevent it with an organization-wide serialization standard (ISO-8601 dates, consistent numeric types) enforced via a shared Jackson configuration library used by every service.
Q25. How do you design an API response envelope so all services look consistent to consumers?
Define one shared response wrapper (e.g., {"data": ..., "error": null, "meta": {"traceId": ...}}) used by every service via a common base library, so a consumer integrating with 10 different internal APIs sees exactly the same top-level shape every time, regardless of which team built the service.

51. Final Summary & Cheat Sheet

Before APIs: tightly coupled direct database access, stale nightly file exports, fragile point-to-point integrations.

REST fundamentals: resource-based URLs, correct HTTP verbs/status codes, DTOs (never expose entities), consistent versioning, pagination, robust error handling, and validation at the boundary.

Swagger/OpenAPI: the backbone of living, always-accurate documentation, interactive testing, and contract-first collaboration across teams.

Beyond REST: GraphQL for flexible, aggregated data-fetching needs (with careful N+1 and query-complexity handling); gRPC for high-throughput internal streaming needs; SOAP still alive in legacy enterprise integrations.

Production readiness: JWT/OAuth2 security, CORS correctly configured, rate limiting, resilience patterns (timeout/retry/circuit breaker/bulkhead/fallback) on every outbound call, correlation IDs for traceability, and full observability tied to Golden Signals.

The golden rule: design the contract first, keep it backward compatible, document it from code (not separately), and treat every downstream/third-party call as something that WILL eventually fail — build resilience in from day one, not after the first outage.
