1. Why Logging Is Needed — Starting with a Simple "Hello World" Application

1.1 The Simplest Possible Program

public class HelloWorldApp {
    public static void main(String[] args) {
        System.out.println("Hello, World!");
    }
}
This works fine — you run it, you see "Hello, World!" in the console, done. But real applications aren't run once by a developer watching the console. They run 24/7, unattended, on remote servers, handling thousands of requests, and something eventually goes wrong when nobody is watching the screen.

1.2 What Happens When This Program Grows Up

public class OrderProcessor {
    public static void main(String[] args) {
        System.out.println("Starting order processing...");
        try {
            processOrder(1001);
        } catch (Exception e) {
            System.out.println("Something went wrong!");   // this tells you NOTHING useful
        }
    }
}
If this ran on a production server last night at 2 AM and failed, all you have is "Something went wrong!" printed into a console window nobody was watching — it's already scrolled away or the terminal was closed. This is the exact problem logging solves.

1.3 The Core Reasons We Need Logging

ReasonSimple Explanation
Nobody watches the console 24/7Logs written to a file/system persist even when no one is looking, so you can check them later
Understand what happened before a crashA log trail shows the sequence of events leading up to a failure
Debug issues that only happen in productionYou can't attach a debugger to a live production server — logs are often your only window into what happened
Track business events"Order #1001 placed by customer #55 at 10:42 AM" — useful for audits, support, and analytics, not just bugs
Security & complianceWho accessed what, when — required for audits in banking/healthcare
Performance analysisLogs with timestamps reveal how long each step took

2. Before Logging Frameworks — What Developers Used to Do

2.1 The print() / System.out.println() Era

Before dedicated logging frameworks existed, Java developers simply used System.out.println() (or System.err.println() for errors) scattered throughout the code. This "worked" for tiny programs but broke down fast in real applications.

2.2 Problems With Using println() in Real Applications

ProblemWhy It Hurts in Production
No log levelsCan't say "only show me errors" — every println prints unconditionally, cluttering output
No timestamps by defaultYou don't know exactly when something happened without manually adding it every time
Nowhere persistent to lookConsole output disappears when the terminal closes or the server restarts
No way to turn off verbose logs in productionYou'd have to comment out code and redeploy just to reduce noise
Can't easily route logs elsewhereNo built-in way to send logs to a file, a database, or a remote log server
Poor performance at scaleUncontrolled, unbuffered console writes across many threads slow down high-traffic applications
No structureFree-form text is hard to search/filter/parse reliably at scale

2.3 A Real Example of the Old Way

// Old-style manual "logging" — common in legacy codebases before Log4j adoption
public class LegacyPaymentService {
    public void processPayment(double amount) {
        System.out.println("[" + new java.util.Date() + "] Processing payment: " + amount);
        try {
            // ... payment logic
        } catch (Exception e) {
            System.out.println("[" + new java.util.Date() + "] ERROR: " + e.getMessage());
            e.printStackTrace();   // prints directly to console, uncontrolled
        }
    }
}
Every developer manually formatted timestamps differently, there was no consistent way to filter by severity, and turning this "off" for production meant physically deleting or commenting out print statements — a real, common pain point that led to the creation of dedicated logging frameworks like Log4j.

3. Introduction to Log4j, SLF4J and Logback in Java

3.1 Why Log4j Was Created

Log4j (created in 1999) was one of the first Java logging frameworks to solve exactly the problems in Section 2 — configurable log levels, multiple output destinations ("appenders": console, file, database, remote server), and configurable message formatting, all without changing code.

3.2 The Modern Java Logging Landscape

ComponentRole
SLF4J (Simple Logging Facade for Java)A common API/facade your code depends on — you write code against SLF4J, and the actual logging framework underneath can be swapped without changing your code
LogbackThe most common modern implementation used underneath SLF4J — Spring Boot's default logging framework
Log4j2The modern successor to the original Log4j — a full-featured framework, an alternative to Logback, often chosen for higher performance async logging
Interview tip: SLF4J is not a logging implementation itself — it's a facade. This means you can code entirely against the SLF4J API and switch the actual underlying engine (Logback vs Log4j2) via dependencies alone, with zero code changes.

3.3 Real Code — Using SLF4J (What You Actually Write in Spring Boot)

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

public class PaymentService {
    private static final Logger log = LoggerFactory.getLogger(PaymentService.class);

    public void processPayment(double amount) {
        log.info("Processing payment of amount={}", amount);
        try {
            // ... payment logic
        } catch (Exception e) {
            log.error("Payment processing failed for amount={}", amount, e);   // e = full stack trace logged
        }
    }
}

// With Lombok, this becomes even shorter:
@Slf4j
public class PaymentService {
    public void processPayment(double amount) {
        log.info("Processing payment of amount={}", amount);
    }
}

3.4 Log4j2 Configuration Example (log4j2.xml)

<Configuration status="WARN">
  <Appenders>
    <Console name="Console" target="SYSTEM_OUT">
      <PatternLayout pattern="%d{yyyy-MM-dd HH:mm:ss} [%t] %-5level %logger{36} - %msg%n"/>
    </Console>
    <RollingFile name="File" fileName="logs/app.log" filePattern="logs/app-%d{yyyy-MM-dd}-%i.log.gz">
      <PatternLayout pattern="%d{ISO8601} [%t] %-5level %logger{36} - %msg%n"/>
      <Policies>
        <TimeBasedTriggeringPolicy/>
        <SizeBasedTriggeringPolicy size="50MB"/>
      </Policies>
      <DefaultRolloverStrategy max="10"/>    <!-- keep last 10 rotated files -->
    </RollingFile>
  </Appenders>
  <Loggers>
    <Logger name="com.bank" level="INFO" additivity="false">
      <AppenderRef ref="Console"/>
      <AppenderRef ref="File"/>
    </Logger>
    <Root level="WARN">
      <AppenderRef ref="Console"/>
    </Root>
  </Loggers>
</Configuration>
This configuration says: log everything INFO and above from com.bank package code to both console and a rotating file (max 50MB per file, gzip old ones, keep last 10) — but only WARN and above for all other (third-party library) code, keeping noise down.

3.5 Spring Boot's Default — Logback (application.yml)

logging:
  level:
    root: WARN
    com.bank: INFO
  file:
    name: logs/accounts-service.log
  pattern:
    file: "%d{ISO8601} [%X{traceId}] %-5level %logger{36} - %msg%n"
Notice %X{traceId} — this pulls a value from the SLF4J MDC (Mapped Diagnostic Context), which is exactly how Correlation IDs and Trace IDs get automatically included in every log line (full detail in Section 9).

5. What Is Observability? Monitoring vs Observability

5.1 What Is Observability?

Observability is the ability to understand what's happening inside a system just by examining its external outputs — logs, metrics, and traces — even for problems you never anticipated in advance. It answers "why" something is happening, not just "that" something is happening.

5.2 What Is Monitoring?

Monitoring is watching a predefined set of metrics/dashboards/alerts for known failure conditions you already anticipated — "CPU > 90%," "error rate > 5%." It tells you that something is wrong.

5.3 Monitoring vs Observability — Side by Side

AspectMonitoringObservability
ApproachWatches known, predefined metrics/dashboardsLets you explore and ask new questions about unknown issues
Answers"Is the system healthy right now?""Why exactly is this specific request slow?"
Good forKnown failure modes (disk full, CPU spike)Novel, first-time-seen production issues
Built fromDashboards and alert rulesLogs + Metrics + Traces combined, richly correlated by IDs
RelationshipMonitoring is a subset of Observability — you need good telemetry data (observability) to build good monitoring on top of it
Interview one-liner: "Monitoring tells you something is broken; observability helps you figure out why — you can have monitoring without full observability, but you can't have real observability without collecting the data monitoring depends on."

6. The Three Pillars of Observability — Logs, Metrics, Traces

The Three Pillars — What Each One Answers
Logs
"What exactly happened?"
Metrics
"How is the system trending over time?"
Traces
"Where did time go for THIS request?"

6.1 Logs

Discrete, timestamped, detailed event records — an error message, a business event, a warning. Best for deep-diving into one specific incident or request.

6.2 Metrics

Numeric measurements aggregated over time — request count, average latency, memory usage percentage. Best for trends, dashboards, and alerting thresholds; cheap to store even at high volume since they're pre-aggregated numbers, not full text.

6.3 Traces

The end-to-end path of a single request as it flows through multiple services/components, broken into timed "spans." Best for finding exactly which hop in a multi-service call chain is slow or failing.

6.4 How They Work Together — Real Example

Using All Three Pillars Together to Debug an Incident
1. Grafana metric dashboard shows: Accounts Service p99 latency spiked to 3s
↓
2. Open Jaeger, find a slow trace from that time window
↓ trace shows one span (Cards Service call) took 2.8s of the 3s
3. Search Kibana/Splunk logs filtered by that trace ID → find the exact error/warning logged by Cards Service at that moment

9. Structured Logging, Correlation ID, Trace ID & Span ID

9.1 Unstructured vs Structured Logging

# Unstructured (plain text) — hard to search/filter reliably at scale
2026-09-30 10:42:13 INFO Order 1001 created for customer 55, amount 4500.00

# Structured (JSON) — every field is queryable, filterable, aggregatable
{"timestamp":"2026-09-30T10:42:13Z","level":"INFO","service":"orders-service",
 "traceId":"a1b2c3d4","message":"Order created","orderId":1001,"customerId":55,"amount":4500.00}
Structured (usually JSON) logs let tools like Splunk/ELK index each field separately — you can query customerId=55 AND level=ERROR directly, instead of writing fragile text-pattern searches across free-form messages.

9.2 Real Spring Boot Structured Logging Setup (Logback JSON Encoder)

<dependency>
  <groupId>net.logstash.logback</groupId>
  <artifactId>logstash-logback-encoder</artifactId>
</dependency>

<!-- logback-spring.xml -->
<appender name="JSON" class="ch.qos.logback.core.ConsoleAppender">
  <encoder class="net.logstash.logback.encoder.LogstashEncoder">
    <includeMdcKeyName>traceId</includeMdcKeyName>
    <includeMdcKeyName>spanId</includeMdcKeyName>
  </encoder>
</appender>

9.3 What Is a Correlation ID?

A Correlation ID is a unique identifier generated at the very start of a request (usually at the API Gateway or the first service that receives it) and passed along in every downstream call's headers/logs — letting you find every log line related to one user's request across every service it touched, just by searching for that one ID.
// Servlet Filter generating/propagating a correlation ID
@Component
public class CorrelationIdFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        String correlationId = req.getHeader("X-Correlation-Id");
        if (correlationId == null) correlationId = UUID.randomUUID().toString();
        MDC.put("correlationId", correlationId);     // now available to every log line via %X{correlationId}
        res.setHeader("X-Correlation-Id", correlationId);
        try {
            chain.doFilter(req, res);
        } finally {
            MDC.clear();     // always clean up MDC to avoid leaking into the next request on the same thread
        }
    }
}

9.4 Trace ID & Span ID (Distributed Tracing Terms)

A Trace ID is essentially a more formal, standardized version of a Correlation ID used specifically by distributed tracing systems (OpenTelemetry, Zipkin, Jaeger) — it identifies the entire end-to-end request across all services. A Span ID identifies one specific unit of work within that trace (e.g., "the Cards Service's handling of this request" is one span, "the SQL query it ran" could be a child span).
Trace ID vs Span ID
Trace ID: 7f3a9c (whole request, same across all services)
Span A: Gateway (id: s1)
Span B: Accounts Service (id: s2, parent: s1)
Span C: Cards Service call (id: s3, parent: s2)
Real scenario: "A customer reports 'my transfer failed.' We ask for the correlation ID from the error screen (or find it via their customer ID + timestamp), search Splunk for that exact ID, and instantly see every log line from Gateway → Accounts Service → Cards Service → Kafka for that one specific request — no guessing which of 50 million daily log lines are relevant."

10. Centralized Logging & Log Aggregation — Why It's Mandatory

10.1 The Problem Without Centralized Logging

With 20 microservices running across dozens of Kubernetes pods, logs sitting only on each pod's local disk are nearly useless — pods are ephemeral (deleted/rescheduled constantly), so their logs vanish, and manually SSHing/kubectl-exec-ing into each pod to grep logs one by one doesn't scale at all.

10.2 What Centralized Logging Provides

  • One searchable place for logs from every service, every pod, every environment.
  • Logs survive even after the pod that generated them is gone.
  • Powerful search/filter across huge volumes (millions of log lines/day) in seconds.
  • Dashboards and alerts built directly on log data (e.g., alert if "ERROR" count spikes).
  • Long-term retention for audits/compliance, independent of any single server's disk.

10.3 General Log Aggregation Architecture (Tool-Agnostic)

Log Aggregation — The Universal Pattern
App writes logs
(stdout or file)
↓
Log Shipper/Agent
(Filebeat, Fluentd, Splunk Forwarder)
↓ ships to
Central Log Store
(Elasticsearch or Splunk Indexer)
↓
Search & Dashboard UI
(Kibana or Splunk Web)
This same 4-layer pattern (App → Shipper → Store → UI) is exactly how both ELK and Splunk work internally — once you understand one, the other is easy to map onto the same mental model, just with different product names.

13. Splunk Deep Dive — Architecture, Indexing, Forwarders

13.1 What Is Splunk?

Splunk is a commercial, enterprise-grade platform for collecting, indexing, and searching machine-generated data (logs, metrics, events) at massive scale — it plays the same overall role as ELK, but as a mature, polished, paid product with a very powerful proprietary query language (SPL) and strong enterprise support/compliance features.

13.2 Splunk Architecture

13.3 Core Splunk Concepts

ConceptMeaning
Universal ForwarderLightweight agent installed on each server/pod that reads log files/stdout and forwards raw data to indexers
IndexWhere Splunk stores processed/indexed event data (e.g., main, or a dedicated bank_prod index)
SourcetypeA classification of the data format (e.g., spring_boot_json, nginx_access) — tells Splunk how to parse fields
EventOne single log entry as stored/indexed in Splunk
Field ExtractionSplunk automatically (or via configured rules) extracts key-value fields from raw events for searching
SPL (Search Processing Language)Splunk's own query language — pipe-based, similar in feel to Unix shell pipelines

Real scenario: "Our Kubernetes pods run without local disk persistence for logs — instead, each Spring Boot service is configured with a Splunk HEC appender that ships structured JSON logs directly over HTTPS the moment they're written, so we don't lose anything even if a pod crashes and is deleted instantly."

14. Splunk Search Processing Language (SPL) — Real Queries

14.1 Basic Search Syntax

# Find all ERROR events from Cards Service in the last 24 hours
index=bank_prod sourcetype=spring_boot_json service="cards-service" level="ERROR"

# Search across a specific time range using earliest/latest
index=bank_prod service="loans-service" earliest=-1h latest=now level="ERROR"

14.2 Real SPL Queries Used in Our Organization

# 1. Count errors per service in the last hour, sorted highest first
index=bank_prod level="ERROR" earliest=-1h
| stats count by service
| sort -count

# 2. Find the full journey of one customer's request using a trace ID
index=bank_prod traceId="a1b2c3d4"
| sort _time
| table _time, service, level, message

# 3. Top 10 slowest API endpoints in the last 4 hours
index=bank_prod sourcetype=access_log earliest=-4h
| stats avg(durationMs) as avg_duration, p95(durationMs) as p95_duration by endpoint
| sort -p95_duration
| head 10

# 4. Detect a spike in failed logins (possible brute-force attempt)
index=bank_prod sourcetype=auth_log message="Failed login"
| bucket _time span=5m
| stats count by _time, sourceIp
| where count > 20

# 5. Calculate error rate percentage over time for an SLO dashboard
index=bank_prod service="accounts-service"
| bucket _time span=5m
| stats count as total, count(eval(level="ERROR")) as errors by _time
| eval error_rate = round((errors/total)*100, 2)

# 6. Find all audit events where a card limit was changed above a threshold
index=bank_prod sourcetype=audit_log action="card_limit_updated" newLimit>100000
| table _time, user, cardId, oldLimit, newLimit

17. Migrating from Browser/Console Logs to Splunk or ELK (Real Migration Path)

17.1 The Starting Point — "We Just Have Browser Dev Tools / Console Logs"

If today the only visibility into issues is opening browser DevTools Console/Network tab, or SSHing into a server to tail a local log file, you have zero centralized observability — nothing is searchable historically, nothing survives a pod restart, and nobody gets alerted automatically when something breaks.

17.2 Step-by-Step Migration Plan

  1. Step 1 — Standardize on structured logging first. Before shipping logs anywhere, switch every service to JSON structured logging (Section 9) with consistent field names (service, level, traceId, message) — garbage in, garbage out otherwise.
  2. Step 2 — Add Correlation/Trace IDs everywhere. Ensure every request gets a unique ID propagated through all services and included in every log line (Section 9.3).
  3. Step 3 — Pick the destination. Confirm Splunk (since your org already has it) as the target — request an index (e.g., bank_prod) and an HEC token, or forwarder deployment, from your Splunk admin team.
  4. Step 4 — Instrument one pilot service first. Don't migrate all 20 services at once — start with one lower-risk service, wire up the Splunk HEC appender or Universal Forwarder, verify events arrive and fields parse correctly.
  5. Step 5 — Build a basic dashboard and one alert for the pilot service. Prove the value early (e.g., an error-rate dashboard + a Slack/PagerDuty alert) before rolling out further.
  6. Step 6 — Roll out to remaining services incrementally, reusing the same sourcetype/index conventions and log format standards established in the pilot.
  7. Step 7 — Decommission ad-hoc access (SSH-based manual log tailing, browser-console-only debugging) once the team trusts and habitually uses Splunk for troubleshooting.
  8. Step 8 — Add distributed tracing (OpenTelemetry) once basic centralized logging is solid, to complete the observability picture (Sections 20-23).

17.3 What About Frontend (React) Logs Currently Only in Browser DevTools?

Frontend errors visible only in a user's browser console are invisible to your team unless the user reports them. Real organizations solve this by shipping frontend errors/logs to the backend (or directly to an observability tool) using a small client-side error reporting layer.
// React — global error boundary + window.onerror reporting to a backend logging endpoint
window.addEventListener('error', (event) => {
  fetch('/api/client-logs', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({
      message: event.message,
      stack: event.error?.stack,
      url: window.location.href,
      traceId: getCurrentTraceId()
    })
  });
});
The backend endpoint receiving these simply logs them (structured JSON, same pipeline as backend logs) into the same Splunk index — so frontend errors become searchable and alertable exactly like backend errors, closing the "we only saw it in dev tools" gap entirely.

21.6 Root Cause Analysis Using Tracing — Real Walkthrough

  1. Grafana alert fires: Accounts Service p95 latency > 1s.
  2. Open Jaeger, filter traces for Accounts Service in that time window, sort by duration descending.
  3. Open the slowest trace — see the span breakdown (Gateway → Accounts → Cards call → DB query).
  4. Spot that the "Cards Service call" span consistently takes 200-300ms, dominating total request time.
  5. Cross-reference Cards Service's own logs (via the same trace ID in Splunk/Kibana) to find the actual root cause (e.g., a slow downstream Card Network API call without a timeout).

22.3 Database Monitoring

  • Connection pool usage (active vs idle vs max) — exhaustion causes new requests to wait/fail.
  • Slow query log / query duration percentiles (Section 36).
  • Replication lag (for read replicas) — stale reads if lag grows.
  • Lock waits/deadlocks — a common hidden cause of intermittent timeouts.

22.4 API Monitoring

  • Per-endpoint request rate, error rate, latency percentiles (not just service-wide averages — one bad endpoint can hide in a good overall average).
  • Status code breakdown (4xx vs 5xx) — 4xx spikes often indicate a client-side/contract issue, not a backend outage.
  • Rate limit rejection counts — helps distinguish "we're down" from "a client is being throttled as designed."

If your SLO is 99.9% success rate, your "error budget" for the month is the remaining 0.1% — a practical way to balance reliability work vs feature velocity: if the error budget is being consumed too fast, the team pauses risky releases and focuses on stability.

26.2 Memory Leak Detection

A memory leak shows as a heap usage graph that keeps climbing over hours/days and never drops back down even after full GC cycles — eventually leading to OutOfMemoryError or repeated OOMKills.
# Step 1: confirm the trend in Grafana — steadily rising heap usage over days despite GC runs
# Step 2: capture a heap dump for analysis (via Actuator or jmap)
curl -o heapdump.hprof http://accounts-service:8081/actuator/heapdump
jmap -dump:live,format=b,file=heapdump.hprof <pid>

# Step 3: analyze with Eclipse MAT (Memory Analyzer Tool) — look at "Leak Suspects" report
# common real culprits: unbounded static caches/Maps, listeners never unregistered, ThreadLocal not cleared
Real scenario: "A slow, multi-day memory creep in Cards Service was traced (via Eclipse MAT's dominator tree) to a static Map<Long, CardDto> cache that was never evicted — every unique card ID ever looked up stayed in memory forever. Fixed by switching to a bounded Caffeine cache with a TTL and max size."

26.3 High CPU Investigation & Thread Dump Analysis

# Step 1: identify the high-CPU JVM process on the host/pod
top -H -p <pid>    # shows per-thread CPU usage

# Step 2: capture a thread dump at that moment
curl http://accounts-service:8081/actuator/threaddump > threaddump.json
jstack <pid> > threaddump.txt

# Step 3: convert the high-CPU thread's native ID (from top -H) to hex, find matching "nid=0x..." in the thread dump
# Step 4: inspect that thread's stack trace to see exactly what code it's stuck executing
Real scenario: "High sustained CPU on Loans Service was traced via thread dump to a regex pattern with catastrophic backtracking, running on every single interest calculation request — visible as dozens of threads all stuck inside the same Pattern.matches() call in their stack traces."

26.4 GC (Garbage Collection) Analysis

# Enable GC logging (Java 9+)
-Xlog:gc*:file=/logs/gc.log:time,uptime:filecount=10,filesize=50M

# Analyze with GCViewer or GCEasy.io — look for:
# - Frequent Full GCs (should be rare)
# - Long pause times (each pause = frozen application, no requests processed)
# - Rising "after GC" heap baseline over time (memory leak indicator)
SymptomLikely CauseFix Direction
Frequent minor GCsToo much short-lived object churn (young gen too small)Tune young generation size, reduce unnecessary object allocation
Long Full GC pausesOld generation filling up, or memory leakIncrease heap, fix leak, consider G1GC/ZGC tuning
Heap baseline keeps rising after each GCMemory leak — objects not being releasedHeap dump analysis (Section 26.2)

26.5 Slow SQL Analysis

# Step 1: Enable slow query logging on the database (MySQL example)
SET GLOBAL slow_query_log = 'ON';
SET GLOBAL long_query_time = 2;   # log queries taking more than 2 seconds

# Step 2: identify the actual slow query and run EXPLAIN on it
EXPLAIN SELECT * FROM transaction WHERE account_id = 1001 AND created_date > '2026-01-01';

# Step 3: check if an index is missing (look for "type: ALL" = full table scan in EXPLAIN output)
CREATE INDEX idx_txn_account_date ON transaction(account_id, created_date);
Real scenario: "A 'random' slowness on the Accounts Service dashboard was traced through a distributed trace's DB-query span, then to the slow query log, revealing a missing composite index on transaction(account_id, created_date) — a query that once took 4.5 seconds dropped to 12ms after adding the index."

29. Interview Questions & Answers (Basic → Advanced → Scenario Based)

Q1. Why do we need logging in an application?
Because production applications run unattended 24/7 — logging provides a persistent, searchable record of what happened, essential for debugging issues after the fact, tracking business events, security auditing, and performance analysis, none of which console output alone can provide.
Q2. What is the difference between monitoring and observability?
Monitoring watches predefined metrics/dashboards for known failure conditions ("is the system healthy?"). Observability provides rich enough telemetry (logs, metrics, traces) to investigate and answer new, previously unanticipated questions about "why" something is happening.
Q3. What are the three pillars of observability?
Logs (detailed event records — "what exactly happened"), Metrics (aggregated numeric trends — "how is the system trending"), and Traces (the end-to-end path of one request across services — "where did time go for this specific request").
Q4. What are the four Golden Signals?
Latency (how long requests take), Traffic (demand on the system), Errors (rate of failures), and Saturation (how full/stressed the system's resources are) — the minimum set of metrics recommended for monitoring any user-facing service.
Q5. What is a Correlation ID and why is it important?
A unique identifier generated at the start of a request and propagated through every downstream service call and log line, letting you find every log related to one specific request across an entire distributed system with a single search.
Q6. Difference between Trace ID and Span ID?
A Trace ID identifies the entire end-to-end request across all services. A Span ID identifies one specific unit of work within that trace (e.g., one service's handling of the request, or one DB query) — spans are linked in a parent-child hierarchy to reconstruct the full call tree.
Q7. What is SLF4J, and why isn't it a logging framework itself?
SLF4J is a facade/API — your code depends on SLF4J's interfaces, while the actual logging implementation (Logback, Log4j2) is plugged in underneath. This lets you switch the underlying logging engine without changing application code.
Q8. Why is DEBUG-level logging risky to leave enabled in production?
It generates a very high volume of log data, increasing storage/ingestion cost (especially with paid tools like Splunk billed on volume), can slow down the application under high load, and risks accidentally logging sensitive data not meant for verbose output.
Q9. How does Prometheus collect metrics, and how is that different from log shipping?
Prometheus uses a pull model — it scrapes a metrics endpoint (like Spring Boot Actuator's /actuator/prometheus) on a schedule. Log shippers (Filebeat, Splunk forwarders) typically push data as it's generated — a key architectural difference often asked about in interviews.
Q10. Explain SLI, SLO, and SLA with an example.
SLI is the actual measured value (e.g., "99.2% success rate this month"). SLO is the internal target (e.g., "we aim for 99.5%"). SLA is the external, often contractual promise to customers (e.g., "99% uptime guaranteed"), deliberately set looser than the SLO to give the team a safety buffer.
Q11. How would you investigate a memory leak in a Spring Boot application in production?
Confirm a steadily rising heap trend in Grafana that doesn't drop after GC, capture a heap dump via Actuator's /actuator/heapdump or jmap, and analyze it with Eclipse MAT's "Leak Suspects" report to find what's holding references — commonly unbounded caches, unregistered listeners, or ThreadLocal misuse.
Real scenario: a static Map cache that was never evicted caused a multi-day memory creep, fixed by switching to a bounded, TTL-based Caffeine cache.
Q12. How would you diagnose high CPU usage on a production JVM?
Use `top -H -p <pid>` to find the specific high-CPU thread, capture a thread dump at that moment (Actuator's /actuator/threaddump or jstack), convert the thread's native ID to hex, and locate its exact stack trace to see what code it's stuck executing.
Q13. What's the difference between Zipkin and Jaeger?
Both are distributed tracing UIs. Zipkin is simpler and lighter, good for smaller scale. Jaeger (from Uber, CNCF) scales further with more storage backend options and a richer service dependency graph UI, making it a common choice for larger Kubernetes-native organizations.
Q14. What is the difference between ELK and Splunk?
Both centralize and search logs at scale. ELK is open-source (with paid tiers) and self-hosted/self-managed by default; Splunk is a commercial product (or Splunk Cloud) with a very powerful SPL query language, generally considered more polished/enterprise-ready but licensed by ingestion volume, which can get expensive at scale.
Q15. How would you migrate an application currently relying only on browser console logs to a centralized tool like Splunk?
Standardize on structured JSON logging with correlation IDs first, pick a pilot service, wire it to Splunk via HEC or a Universal Forwarder, validate field parsing and build one dashboard/alert to prove value, then roll out incrementally to remaining services — and separately, add a client-side error handler in the frontend that ships browser errors to a backend logging endpoint so they land in the same centralized system.
Q16. What is the purpose of readiness and liveness probes, and how do they relate to Actuator?
Readiness (/actuator/health/readiness) tells Kubernetes if a pod should currently receive traffic — failing it removes the pod from load balancing without restarting it. Liveness (/actuator/health/liveness) tells Kubernetes if the pod is alive at all — failing it triggers a container restart.
Q17. How do you find the root cause of a slow multi-service request?
Use distributed tracing to find the specific slow span in the call chain (e.g., via Jaeger or Application Insights), then cross-reference centralized logs (Splunk/Kibana) filtered by the same trace ID to see the detailed context/error for that exact slow component.
Q18. What should you never log, and why?
Passwords, full card numbers, JWT tokens, and other sensitive PII/PCI data — logging them in plain text creates serious compliance risk (PCI-DSS/GDPR) and a major security exposure if logs are ever leaked or accessed by unauthorized users; mask/redact sensitive fields before logging.
Q19. What is an error budget and how is it used?
The allowed amount of failure implied by an SLO (e.g., a 99.9% SLO implies a 0.1% error budget). Teams use it to balance reliability and feature velocity — if the budget is being consumed too fast, the team pauses risky releases to focus on stability instead.
Q20. Walk through a real production incident you resolved using logs, metrics, and traces together.
An alert fired on high error rate (metrics); a distributed trace showed the failure occurred in a downstream Cards Service call (traces); searching centralized logs by that request's trace ID revealed the exact exception — a third-party Card Network API timeout (logs) — while the circuit breaker's fallback kept the system functioning in a degraded but stable state during the incident.

30. Final Summary & Cheat Sheet

The journey: System.out.println() → Log4j/SLF4J/Logback with levels and files → Centralized logging (Splunk/ELK) with structured JSON and correlation IDs → Full observability (Logs + Metrics + Traces) with Prometheus/Grafana, OpenTelemetry/Jaeger/Zipkin, and Actuator/Micrometer.

Our real stack: Splunk for centralized log search and SPL-powered dashboards/alerts, Azure Monitor/Prometheus+Grafana for metrics, Application Insights/Jaeger for distributed tracing, Alertmanager/PagerDuty for incident notification — all integrated with our Azure DevOps pipelines for deployment-correlated observability.

The golden rule: Instrument for observability from day one (structured logs, correlation IDs, health probes, basic metrics) rather than bolting it on after the first painful production incident where nobody could figure out what went wrong.
