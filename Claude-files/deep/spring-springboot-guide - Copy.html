1. Before Spring — The Evolution of Java Enterprise Development

1.1 The Starting Point — Plain Java (Core Java)

Java began as a general-purpose language — classes, objects, methods, no built-in concept of "web application." To build a web application in early Java, developers needed additional specifications and containers on top of Core Java.

2. Introduction to Servlets — What They Are and Their Problems

2.1 What Is a Servlet?

A Servlet is a Java class that runs inside a Servlet Container (like Apache Tomcat) and handles HTTP requests/responses directly — it's the foundational building block that every Java web framework (Struts, Spring MVC, Spring Boot) is ultimately built on top of.

2.2 A Real, Raw Servlet

public class AccountServlet extends HttpServlet {
    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp)
            throws ServletException, IOException {
        String accountId = req.getParameter("id");
        Account account = accountDao.findById(Long.parseLong(accountId));   // manual lookup

        resp.setContentType("text/html");
        PrintWriter out = resp.getWriter();
        out.println("<html><body>");
        out.println("<h1>Balance: " + account.getBalance() + "</h1>");   // HTML hardcoded directly in Java!
        out.println("</body></html>");
    }
}

<!-- web.xml — manual URL mapping, no annotations in early Servlet versions -->
<servlet>
  <servlet-name>AccountServlet</servlet-name>
  <servlet-class>com.bank.AccountServlet</servlet-class>
</servlet>
<servlet-mapping>
  <servlet-name>AccountServlet</servlet-name>
  <url-pattern>/account</url-pattern>
</servlet-mapping>

2.3 Real Problems With Raw Servlets

  • HTML mixed with Java code — printing HTML tags via out.println() is unmaintainable for any real UI.
  • One servlet class per URL, or a lot of manual if/else routing logic inside a single servlet — no clean routing framework.
  • Verbose XML configuration (web.xml) for every servlet mapping.
  • No separation of concerns — a single class often handled request parsing, business logic, and HTML rendering.
  • No built-in dependency injection — objects were manually instantiated (new AccountDao()) everywhere, making unit testing hard.
JSP (JavaServer Pages) was introduced specifically to fix the "HTML mixed with Java" problem by flipping the model — write HTML normally, embed small Java snippets only where needed (<% %> scriptlets) — but this created its own mess of business logic leaking into view pages, which MVC frameworks like Struts and later Spring MVC solved properly (Section 20).

3. JDBC — Direct Database Access Before ORM

3.1 What Is JDBC?

JDBC (Java Database Connectivity) is the standard low-level API for connecting Java applications to relational databases — every ORM (including Hibernate) is ultimately built on top of JDBC underneath.

3.2 Real Raw JDBC Code (What Developers Wrote Before Hibernate)

public Account findAccountById(Long id) {
    Connection conn = null;
    PreparedStatement stmt = null;
    ResultSet rs = null;
    try {
        conn = DriverManager.getConnection(DB_URL, USER, PASSWORD);   // manual connection management
        stmt = conn.prepareStatement("SELECT * FROM account WHERE id = ?");
        stmt.setLong(1, id);
        rs = stmt.executeQuery();
        if (rs.next()) {
            Account account = new Account();
            account.setId(rs.getLong("id"));                 // manual column-by-column mapping
            account.setBalance(rs.getBigDecimal("balance"));
            account.setStatus(rs.getString("status"));
            return account;
        }
        return null;
    } catch (SQLException e) {
        throw new RuntimeException(e);
    } finally {
        // manual resource cleanup — easy to forget, causes connection leaks
        try { if (rs != null) rs.close(); } catch (SQLException ignored) {}
        try { if (stmt != null) stmt.close(); } catch (SQLException ignored) {}
        try { if (conn != null) conn.close(); } catch (SQLException ignored) {}
    }
}

3.3 Real Problems With Raw JDBC

ProblemWhy It Hurts
Enormous boilerplateThe same connection/statement/resultset/cleanup pattern repeated for every single query
Manual object mappingEvery row-to-object mapping written by hand, error-prone and tedious at scale
Easy to leak resourcesForgetting to close a Connection/Statement/ResultSet in the finally block causes connection pool exhaustion over time
No object relationshipsFetching an Account with its Cards required manually writing and combining multiple queries by hand
SQL scattered everywhereRaw SQL strings embedded directly in Java code across the codebase, hard to maintain/refactor
This exact pain — repetitive boilerplate and manual object mapping — is precisely what Hibernate/JPA (Section 4) and later Spring's JdbcTemplate/Spring Data JPA were built to eliminate.

4. Hibernate & ORM Evolution

4.1 What Is ORM (Object-Relational Mapping)?

ORM maps Java objects directly to database tables/rows, letting developers work with regular Java objects and let the framework generate and execute the actual SQL — Hibernate was the dominant Java ORM implementation that made this mainstream in the early-to-mid 2000s.

4.2 The Same Query, With Hibernate

@Entity
@Table(name = "account")
public class Account {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private BigDecimal balance;
    private String status;
    // getters/setters
}

// Fetching — Hibernate handles connection, SQL generation, and object mapping automatically
Session session = sessionFactory.openSession();
Account account = session.get(Account.class, id);   // ONE line replaces the entire raw JDBC method from Section 3.2

4.3 JPA vs Hibernate — A Common Point of Confusion

JPAHibernate
What it isA specification (interfaces/annotations) — @Entity, @Id, EntityManagerA concrete implementation of that specification (the actual working code)
AnalogyLike an interfaceLike a class implementing that interface
Alternatives—EclipseLink, OpenJPA are other JPA implementations
Interview tip: When you use @Entity and EntityManager in a Spring Boot app, you're coding against the JPA specification; Spring Boot's default underlying implementation providing the actual behavior is Hibernate.

4.4 What Hibernate/JPA Solved (and What Still Needed Solving)

  • Eliminated manual SQL/ResultSet mapping boilerplate.
  • Provided caching, lazy loading, and relationship management (@OneToMany, @ManyToOne) out of the box.
  • Still needed: a way to wire together DAOs/Services/Controllers cleanly, manage transactions declaratively, and avoid manually creating a SessionFactory/EntityManagerFactory in every application — exactly the gap Spring Framework filled next.

5. Introduction to Spring Framework — Why It Was Created

5.1 The Problem Spring Solved (2003)

At the time, "Enterprise Java" meant heavyweight EJB (Enterprise JavaBeans) — requiring a full EJB container, verbose boilerplate interfaces, and painfully slow development/testing cycles. Rod Johnson created Spring as a lightweight alternative built on plain old Java objects (POJOs) and Dependency Injection, proving you could get enterprise-grade features (transactions, security) without EJB's heaviness.

5.2 Spring's Core Idea

Instead of your code creating and wiring its own dependencies (new AccountDao() scattered everywhere), you describe what your objects need, and the Spring IoC Container creates and injects them for you — objects become simple, testable POJOs with no framework-specific base classes to extend (unlike EJB).

6. Introduction to Spring MVC

6.1 What Spring MVC Added on Top of Spring Core

Spring MVC is Spring's own web framework — built on top of the Servlet API, providing a clean Model-View-Controller structure, annotation-based routing (@RequestMapping), and automatic data binding/validation, replacing the need for older frameworks like Struts.

6.2 A Quick Preview (Full Detail in Section 21+)

@Controller
public class AccountController {
    @Autowired
    private AccountService accountService;   // Spring injects this automatically — no "new"

    @GetMapping("/account/{id}")
    public String getAccount(@PathVariable Long id, Model model) {
        model.addAttribute("account", accountService.findById(id));
        return "accountView";   // name of a view (JSP/Thymeleaf template) to render
    }
}
Notice how dramatically cleaner this is than the raw Servlet in Section 2.2 — no manual HTML printing, no manual object creation, clean separation between routing (@GetMapping), business logic (accountService), and rendering (the returned view name).

7. Introduction to Spring Boot

7.1 The Problem Spring Boot Solved (2014)

Plain Spring (even Spring MVC) still required substantial manual configuration — XML or Java config classes wiring up a DataSource, a ViewResolver, a TransactionManager, and deploying a WAR file to an external Tomcat server you had to install and configure yourself. Spring Boot was created to eliminate nearly all of this via auto-configuration and embedded servers.

7.2 What Spring Boot Actually Adds

FeatureWhat It Means
Auto ConfigurationSpring Boot inspects what's on your classpath and automatically configures beans you'd otherwise wire manually (Section 33)
Starter DependenciesOne dependency (e.g., spring-boot-starter-web) pulls in everything needed for a typical use case (Section 34)
Embedded ServerTomcat/Jetty/Undertow is embedded directly in your JAR — just run java -jar app.jar, no separate server install (Section 38)
Opinionated DefaultsSensible defaults for everything, all overridable via application.yml (Section 35)
Production-Ready FeaturesActuator gives health checks/metrics out of the box (Section 37)

7.3 A Complete, Runnable Spring Boot App (Minimal)

@SpringBootApplication
public class BankApplication {
    public static void main(String[] args) {
        SpringApplication.run(BankApplication.class, args);   // starts embedded Tomcat + entire Spring context
    }
}
This is the entire bootstrap needed — no web.xml, no external server install, no manual DataSource/ViewResolver XML configuration for typical use cases. This is precisely why Spring Boot became the default choice for virtually all new Java web/microservices development.

12. Spring Core — The IOC Container

12.1 What Is Inversion of Control (IoC)?

Normally, your code controls object creation (new AccountService()). With IoC, that control is "inverted" — a container creates and manages your objects (called Beans) for you, and hands them to whoever needs them. You describe dependencies; the container resolves and provides them.

13. Dependency Injection — Types and Real Examples

13.1 The Three Types of Dependency Injection

TypeHowRecommended?
Constructor InjectionDependencies passed via the constructorYes — the recommended default for mandatory dependencies
Setter InjectionDependencies set via a setter methodUsed for optional dependencies
Field Injection@Autowired directly on a fieldDiscouraged in production code — harder to unit test, hides required dependencies

13.2 Real Code — All Three Types

// Constructor Injection (RECOMMENDED) — dependencies are final, impossible to construct in an invalid state
@Service
public class AccountService {
    private final AccountRepository accountRepository;
    private final EmailService emailService;

    public AccountService(AccountRepository accountRepository, EmailService emailService) {
        this.accountRepository = accountRepository;
        this.emailService = emailService;
    }
}

// With Lombok, even shorter:
@Service
@RequiredArgsConstructor   // generates the constructor automatically for all final fields
public class AccountService {
    private final AccountRepository accountRepository;
    private final EmailService emailService;
}

// Setter Injection
@Service
public class ReportService {
    private NotificationService notificationService;   // optional dependency

    @Autowired(required = false)
    public void setNotificationService(NotificationService notificationService) {
        this.notificationService = notificationService;
    }
}

// Field Injection (DISCOURAGED)
@Service
public class LegacyService {
    @Autowired
    private AccountRepository accountRepository;   // works, but can't be made final, hard to unit test without reflection
}
Interview tip: Constructor injection is preferred because it makes dependencies explicit and immutable (final), fails fast at startup if a dependency is missing, and makes unit testing trivial — you just call new AccountService(mockRepo, mockEmailService) without needing Spring or reflection tricks at all.

13.3 Resolving Ambiguity — @Qualifier and @Primary

public interface NotificationSender { void send(String message); }

@Service("smsSender")
public class SmsSender implements NotificationSender { ... }

@Service("emailSender")
@Primary   // used by default when multiple candidates exist and no @Qualifier is specified
public class EmailSender implements NotificationSender { ... }

@Service
public class AlertService {
    private final NotificationSender sender;

    public AlertService(@Qualifier("smsSender") NotificationSender sender) {   // explicitly picks the SMS bean
        this.sender = sender;
    }
}

@Component
public class ConnectionPoolManager {

    @PostConstruct
    public void init() {
        log.info("Initializing connection pool...");   // runs once, right after dependency injection completes
    }

    @PreDestroy
    public void cleanup() {
        log.info("Closing connection pool gracefully...");   // runs during graceful application shutdown
    }
}
Real scenario: "Our Kafka consumer service uses @PreDestroy to finish processing any in-flight message and commit its offset before the pod actually terminates during a Kubernetes rolling deployment — without this, a mid-shutdown pod kill could silently drop a message."

@Component
@Scope("prototype")
public class ReportGenerator { ... }   // a new instance every time it's injected/requested
Common mistake: Injecting a prototype-scoped bean into a singleton-scoped bean via normal field/constructor injection only creates the prototype bean once (at singleton creation time) — you need a special pattern (ObjectProvider or a scoped proxy) to actually get a fresh prototype instance on every use.

20. AOP — Aspect Oriented Programming

20.1 What Problem AOP Solves

Cross-cutting concerns (logging, security checks, transaction management, auditing) would otherwise need to be repeated in every single business method. AOP lets you define this logic once, as an "Aspect," and apply it declaratively across many methods/classes matching a pattern ("Pointcut") — without cluttering the actual business logic.

20.2 Core AOP Terminology

TermMeaning
AspectA module encapsulating a cross-cutting concern (e.g., a LoggingAspect class)
AdviceThe actual action taken (what code runs) — Before, After, Around, AfterReturning, AfterThrowing
PointcutAn expression defining WHICH methods the advice applies to
Join PointA specific point during execution (e.g., a method call) where an aspect can be applied
WeavingThe process of applying aspects to target objects (Spring does this at runtime via proxies)

20.3 Real AOP Code — Logging Every Service Method's Execution Time

@Aspect
@Component
public class PerformanceLoggingAspect {

    @Around("execution(* com.bank.accounts.service.*.*(..))")   // Pointcut: every method in the service package
    public Object logExecutionTime(ProceedingJoinPoint joinPoint) throws Throwable {
        long start = System.currentTimeMillis();
        Object result = joinPoint.proceed();   // actually calls the real method
        long duration = System.currentTimeMillis() - start;
        log.info("{} executed in {}ms", joinPoint.getSignature(), duration);
        return result;
    }
}

20.4 Real AOP Code — Custom @Auditable Annotation (Recap From API Guide)

@Aspect
@Component
public class AuditAspect {
    @Around("@annotation(Auditable)")
    public Object audit(ProceedingJoinPoint joinPoint) throws Throwable {
        String user = SecurityContextHolder.getContext().getAuthentication().getName();
        Object result = joinPoint.proceed();
        auditLogRepository.save(new AuditLog(user, joinPoint.getSignature().getName(), Instant.now()));
        return result;
    }
}

20.5 How AOP Actually Works Under the Hood

Spring AOP creates a proxy object wrapping your real bean — when you call a method, you're actually calling the proxy first, which runs the aspect logic and then delegates to the real method. This is why @Transactional/AOP-based advice doesn't work when calling a method on this from within the same class — that internal call bypasses the proxy entirely.
Common gotcha: If method A calls method B in the same class, and B has @Transactional, calling A won't trigger B's transaction behavior — because the call goes directly (this.B()), never passing through the Spring-generated proxy. Real fix: move B into a separate bean/service and inject it, or use AopContext.currentProxy() (less clean).

24. View Resolver

24.1 What ViewResolver Does

31. Interceptors

31.1 What Interceptors Do

A HandlerInterceptor lets you run code before, after, or around controller method execution — similar in spirit to AOP (Section 20) but specifically integrated into the Spring MVC request lifecycle, commonly used for logging, authentication checks, and adding common response headers.

31.2 Real Interceptor Implementation

@Component
public class RequestTimingInterceptor implements HandlerInterceptor {

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
        request.setAttribute("startTime", System.currentTimeMillis());
        return true;   // returning false stops the request here — the controller method never runs
    }

    @Override
    public void afterCompletion(HttpServletRequest request, HttpServletResponse response, Object handler, Exception ex) {
        long start = (Long) request.getAttribute("startTime");
        log.info("{} took {}ms", request.getRequestURI(), System.currentTimeMillis() - start);
    }
}

// Registration
@Configuration
public class WebConfig implements WebMvcConfigurer {
    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(new RequestTimingInterceptor())
                .addPathPatterns("/api/**")
                .excludePathPatterns("/api/v1/auth/**");   // skip auth endpoints
    }
}

  • JSP files must be compiled by a Servlet container — can't easily be unit tested standalone or previewed outside a running server.

33. Spring Boot — Auto Configuration Explained

33.1 How Auto Configuration Actually Works

When your application starts, Spring Boot inspects what's on the classpath (which JAR dependencies are present) and conditionally registers beans you would otherwise have to configure manually — e.g., seeing spring-boot-starter-data-jpa and a database driver on the classpath, it automatically configures a DataSource, an EntityManagerFactory, and a TransactionManager.

33.2 The Mechanism — @Conditional Annotations

// Simplified version of what a real Spring Boot auto-configuration class looks like internally
@Configuration
@ConditionalOnClass(DataSource.class)              // only activates if DataSource is on the classpath
@ConditionalOnMissingBean(DataSource.class)         // only activates if the developer hasn't already defined their own DataSource bean
@EnableConfigurationProperties(DataSourceProperties.class)
public class DataSourceAutoConfiguration {
    @Bean
    public DataSource dataSource(DataSourceProperties properties) {
        return properties.initializeDataSourceBuilder().build();
    }
}

42. Spring Transactions — @Transactional Deep Dive

42.1 What a Transaction Is (Recap)

A transaction is a unit of work that must either fully succeed (commit) or fully fail (rollback) as one atomic operation — e.g., "debit account A and credit account B" must never partially apply.

42.2 How @Transactional Actually Works — AOP Proxies

Just like other AOP-based features (Section 20), @Transactional works via a Spring-generated proxy wrapping your bean — when a transactional method is called externally, the proxy opens a transaction, calls your real method, then commits or rolls back based on the outcome. This is exactly why the "self-invocation" gotcha (Section 20.5) applies to @Transactional too.

42.3 Real Code

@Service
@RequiredArgsConstructor
public class TransferService {
    private final AccountRepository accountRepository;

    @Transactional
    public void transfer(Long fromId, Long toId, BigDecimal amount) {
        Account from = accountRepository.findById(fromId).orElseThrow();
        Account to = accountRepository.findById(toId).orElseThrow();

        from.debit(amount);
        to.credit(amount);

        accountRepository.save(from);
        accountRepository.save(to);
        // if ANY exception is thrown anywhere above, EVERYTHING here rolls back automatically
    }
}

42.5 Where to Put @Transactional — Real Practice

Best practice: Put @Transactional on Service layer methods, never on Controllers (HTTP concerns shouldn't dictate transaction boundaries) and never on Repository methods individually (a single business operation often spans multiple repository calls that must succeed/fail together, as shown in Section 42.3).

43. Transaction Propagation

43.1 What Propagation Controls

Propagation defines what happens when a @Transactional method is called from within another method that's already running inside a transaction — does it join the existing one, or start a completely separate one?

43.2 The Propagation Types

PropagationBehaviorReal Use Case
REQUIRED (default)Joins the existing transaction if one exists, otherwise creates a new oneThe vast majority of service methods — normal business operations
REQUIRES_NEWAlways suspends any existing transaction and starts a brand-new, independent oneAudit logging that must be saved even if the main business transaction later rolls back
NESTEDCreates a savepoint within the existing transaction — can roll back to that savepoint without rolling back the whole outer transactionA sub-step that might fail and needs partial rollback without aborting everything
SUPPORTSJoins an existing transaction if present, otherwise runs non-transactionallyRead operations that don't strictly require a transaction but can use one if available
NOT_SUPPORTEDSuspends any existing transaction and runs without oneRare — a long-running read that shouldn't hold a DB transaction/lock open
MANDATORYMust run within an existing transaction — throws an exception if none existsEnforcing that a method is never called standalone, only as part of a larger transactional flow
NEVERMust NOT run within a transaction — throws an exception if one existsRare edge cases

43.3 Real Example — REQUIRES_NEW for Audit Logging

@Service
@RequiredArgsConstructor
public class LoanService {
    private final AuditService auditService;

    @Transactional
    public void approveLoan(Long loanId) {
        Loan loan = loanRepository.findById(loanId).orElseThrow();
        loan.approve();
        loanRepository.save(loan);

        auditService.logApproval(loanId);   // runs in its OWN independent transaction

        if (someRiskCheckFails()) {
            throw new RuntimeException("Risk check failed after approval");   // rolls back the loan approval...
        }
    }
}

@Service
public class AuditService {
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void logApproval(Long loanId) {
        auditLogRepository.save(new AuditLog("LOAN_APPROVED", loanId));
        // ...but this audit record is ALREADY COMMITTED in its own transaction — it survives the rollback above!
    }
}

44. Transaction Isolation Levels

44.1 What Isolation Controls

Isolation defines how much one transaction can "see" the uncommitted or concurrently-changing data of another transaction running at the same time — a direct tradeoff between data consistency and performance/concurrency.

44.2 The Isolation Levels and the Problems They Prevent

Isolation LevelPreventsStill Allows
READ_UNCOMMITTEDNothingDirty reads, non-repeatable reads, phantom reads (rarely used in practice)
READ_COMMITTED (common default, e.g., PostgreSQL)Dirty readsNon-repeatable reads, phantom reads
REPEATABLE_READ (MySQL's default)Dirty reads, non-repeatable readsPhantom reads (mostly, depends on DB implementation)
SERIALIZABLEDirty reads, non-repeatable reads, phantom reads (fully serial-equivalent execution)Nothing — strongest, but slowest and most lock-heavy

44.3 The Three Core Anomalies, Explained Simply

  • Dirty Read: Transaction A reads data that Transaction B has changed but not yet committed — if B then rolls back, A read data that never really existed.
  • Non-Repeatable Read: Transaction A reads the same row twice, but gets different values because Transaction B updated and committed that row in between A's two reads.
  • Phantom Read: Transaction A runs the same query twice, but gets a different number of rows because Transaction B inserted/deleted a matching row in between.

44.4 Real Code — Setting Isolation Explicitly

    // used sparingly — e.g., for a critical financial reconciliation step where correctness
    // matters more than throughput, since SERIALIZABLE can cause more lock contention/retries
}

Our monthly interest calculation batch job — which reads and aggregates across the entire accounts table and absolutely cannot tolerate phantom reads — explicitly uses SERIALIZABLE isolation, accepting the performance cost for correctness during that one critical process."

45. Rollback Handling

45.1 The Default Rollback Rule (A Very Common Interview Trap)

Critical default behavior: By default, Spring only rolls back a transaction automatically for unchecked exceptions (RuntimeException and its subclasses, plus Error) — checked exceptions do NOT trigger a rollback by default. This surprises many developers coming from a "any exception should roll back" assumption.

45.2 Real Example of the Trap

@Transactional
public void processPayment(PaymentRequest request) throws PaymentGatewayException {   // CHECKED exception
    paymentRepository.save(new Payment(request));
    if (gatewayCallFails()) {
        throw new PaymentGatewayException("Gateway timeout");   // checked — does NOT roll back by default!
    }
    // the Payment record above STAYS COMMITTED even though the gateway call failed — a real bug waiting to happen
}

45.3 The Fix — rollbackFor

@Transactional(rollbackFor = PaymentGatewayException.class)   // now explicitly rolls back for this checked exception too
public void processPayment(PaymentRequest request) throws PaymentGatewayException { ... }

// Or the inverse — prevent rollback for a specific exception that's expected/non-fatal
@Transactional(noRollbackFor = MinorValidationWarning.class)
public void processWithWarnings() { ... }

45.4 Programmatic Rollback (Manual Control)

@Transactional
public void conditionalProcess() {
    if (someBusinessConditionFails()) {
        TransactionAspectSupport.currentTransactionStatus().setRollbackOnly();   // force a rollback without throwing an exception
        return;
    }
    // normal processing continues
}
Interview tip: Always explicitly review whether your custom exceptions are checked or unchecked, and use rollbackFor deliberately rather than assuming Spring's default rollback behavior matches your business expectations — this exact gotcha has caused real production data-consistency bugs at many organizations.

46. Distributed Transactions

46.1 Why Local @Transactional Isn't Enough Across Microservices

Everything in Sections 42-45 works for a single database within a single service. Once a business operation spans multiple microservices with separate databases (e.g., Loans Service + Accounts Service), there's no single local transaction that can span both — this is exactly the problem the Saga Pattern (Microservices guide, Section 22) solves.

46.2 Two-Phase Commit (2PC) — The Older Approach

2PC uses a transaction coordinator to ask all participants to "prepare" (lock resources, ready to commit), then tells everyone to actually "commit" only if all participants confirmed readiness — technically possible via JTA (Java Transaction API) but rarely used in modern microservices due to blocking behavior, tight coupling, and poor availability characteristics (if the coordinator or any participant is down, everything blocks).

46.3 The Modern Approach — Saga Pattern (Recap)

Full detail already in the Microservices guide (Section 22) — break the distributed operation into a sequence of local @Transactional steps, each in its own service, with compensating actions to undo earlier steps if a later one fails, trading strict atomicity for eventual consistency with guaranteed rollback logic.
Local @Transactional vs Distributed Saga
Single Service: @Transactional handles atomicity automatically within one DB
— vs —

→
Accounts Service: @Transactional (local step 2)
→

Interview tip: "@Transactional guarantees atomicity within a single database/service. Across microservices, we don't try to force a distributed transaction — we use the Saga pattern, where each service's own local @Transactional method handles its own piece, and a compensating transaction undoes it if a later step in the saga fails."

48. Mockito

48.1 Why Mocking Matters

A true unit test should test ONE class in isolation — Mockito lets you create fake ("mock") versions of a class's dependencies, so you can test business logic without needing a real database, a real network call, or a real third-party API.

@ExtendWith(MockitoExtension.class)

    @Mock

49.1 What MockMvc Tests

@WebMvcTest(AccountController.class)   // only loads the web layer, NOT the full application context — fast

52.4 Real Code — Full Cache Lifecycle

@Service
@CacheConfig(cacheNames = "accounts")
@RequiredArgsConstructor
public class AccountService {
    private final AccountRepository accountRepository;

    @Cacheable(key = "#id")
    public AccountDto findById(Long id) {
        log.info("Cache MISS — hitting the database for account {}", id);   // only logs on an actual cache miss
        return mapper.toDto(accountRepository.findById(id).orElseThrow());
    }

    @CachePut(key = "#result.id")   // always runs, then refreshes the cache with the updated value
    public AccountDto updateAccount(Long id, UpdateAccountRequest request) {
        Account account = accountRepository.findById(id).orElseThrow();
        account.updateFrom(request);
        return mapper.toDto(accountRepository.save(account));
    }

    @CacheEvict(key = "#id")   // removes the stale entry so the next read is a fresh cache miss
    public void closeAccount(Long id) {
        accountRepository.deleteById(id);
    }

    @CacheEvict(allEntries = true)   // nukes the ENTIRE "accounts" cache — used sparingly, e.g., after a bulk import job
    public void evictAllAccountsCache() { }
}

@Service
@RequiredArgsConstructor
public class SessionTokenService {
    private final RedisTemplate<String, String> redisTemplate;

    public void storeToken(String sessionId, String token) {
        redisTemplate.opsForValue().set("session:" + sessionId, token, Duration.ofMinutes(15));   // with TTL
    }

    public String getToken(String sessionId) {
        return redisTemplate.opsForValue().get("session:" + sessionId);
    }

    public void incrementLoginAttempts(String username) {
        redisTemplate.opsForValue().increment("login-attempts:" + username);   // atomic counter — great for rate limiting
    }
}

53.6 Redis Eviction Policies (What Happens When Redis Runs Out of Memory)

PolicyBehavior
noevictionRejects new writes once memory is full — errors instead of losing data (risky for a pure cache use case)
allkeys-lruEvicts the Least Recently Used key across all keys — the most common choice for a pure cache
volatile-lruEvicts LRU only among keys that have a TTL set, leaving permanent keys untouched
allkeys-randomEvicts a random key — rarely the best choice, but very cheap to compute

53.7 Redis Cache Invalidation — The Hardest Problem in Caching

"There are only two hard things in computer science: cache invalidation and naming things." Real bugs happen when an update path forgets to evict/refresh the cache — e.g., updating a card limit directly via a batch SQL script bypasses @CachePut/@CacheEvict entirely, leaving Redis serving a stale limit until the TTL expires.
Real scenario: "A production incident once involved a customer seeing an outdated card limit after our support team manually corrected a data issue directly in the database — bypassing the application layer entirely meant Redis never got evicted. We fixed the process by requiring all manual data corrections to go through an authenticated internal API endpoint that properly triggers cache eviction, never direct SQL against production."

57. Interview Questions & Answers (Basic → Advanced → Scenario Based)

Q1. What problem does Spring solve, and why was it created?
Spring was created as a lightweight alternative to heavyweight EJB, using Dependency Injection and plain POJOs to provide enterprise features (transactions, AOP) without requiring an EJB container or framework-specific base classes — making applications simpler to build and unit test.
Q2. What is the difference between Spring, Spring MVC, and Spring Boot?
Spring (Core) provides the IoC container and dependency injection; Spring MVC is a web framework built on top of Spring Core; Spring Boot is a convention-over-configuration layer on top of both, adding auto-configuration, starter dependencies, and embedded servers — they're layered, not competing.
Q3. Explain the three types of Dependency Injection and which is recommended.
Constructor, setter, and field injection. Constructor injection is recommended — it makes dependencies explicit and immutable (final fields), fails fast at startup if something's missing, and makes unit testing trivial without needing Spring or reflection.
Q4. Walk through the Spring Bean lifecycle.
Instantiate (constructor called) → Populate Properties (DI happens) → Aware interfaces invoked → @PostConstruct/InitializingBean (custom init logic) → bean is ready and in use → @PreDestroy/DisposableBean during shutdown for cleanup.
Q5. What's the difference between singleton and prototype bean scope, and what's a common gotcha?
Singleton creates exactly one shared instance per container (the default); prototype creates a new instance every time it's requested. The gotcha: injecting a prototype bean into a singleton via normal injection only creates it once at singleton-creation time — you need ObjectProvider or a scoped proxy to actually get fresh instances per use.
Q6. Explain AOP and how Spring implements it.
AOP lets you define cross-cutting concerns (logging, auditing, transactions) once as an "Aspect" and apply them declaratively via Pointcuts, instead of repeating the logic in every method. Spring implements this via runtime proxies wrapping your beans — calling a method actually calls the proxy first, which runs the aspect logic, then delegates to your real method.
Q7. Walk through the complete Spring MVC request flow.
A request hits DispatcherServlet (Front Controller) → HandlerMapping determines which controller method handles it → the Controller executes (calling the service layer, populating the Model) → it returns a logical view name → ViewResolver resolves it to an actual View → the View renders using Model data → DispatcherServlet sends the final response.
Q8. How does Spring Boot's auto-configuration actually work?
At startup, Spring Boot inspects the classpath and conditionally registers beans (via @ConditionalOnClass, @ConditionalOnMissingBean, etc.) that a typical use case would need — e.g., seeing a JPA starter and a DB driver auto-configures a DataSource and EntityManagerFactory. Defining your own bean of the same type automatically disables the auto-configured one.
Q9. What are Spring Profiles and why are they important?
Profiles let the exact same built artifact run with different configuration per environment (application-dev.yml, application-prod.yml) activated via --spring.profiles.active — critical for the "build once, promote everywhere" CI/CD principle, avoiding rebuilding the artifact per environment.
Q10. Explain @Transactional propagation, specifically REQUIRED vs REQUIRES_NEW.
REQUIRED (the default) joins an existing transaction if one is active, or creates a new one if not — if the outer transaction rolls back, everything inside it rolls back too. REQUIRES_NEW always suspends any existing transaction and starts an independent one that commits/rolls back on its own — useful for audit logs that must persist even if the main business transaction later fails.
Real scenario: Logging a loan approval audit record with REQUIRES_NEW ensures the audit trail survives even if a later risk check causes the main approval transaction to roll back.
Q11. Why doesn't Spring roll back a transaction for a checked exception by default, and how do you fix it?
Spring's default rollback rule only covers unchecked exceptions (RuntimeException/Error) — checked exceptions require explicitly specifying rollbackFor = YourCheckedException.class on @Transactional, otherwise the transaction commits even though an exception was thrown, a common real production bug.
Q12. What are the transaction isolation levels, and what problem does each prevent?
READ_UNCOMMITTED prevents nothing; READ_COMMITTED prevents dirty reads; REPEATABLE_READ additionally prevents non-repeatable reads; SERIALIZABLE prevents all three anomalies (dirty reads, non-repeatable reads, phantom reads) at the cost of the most locking/performance overhead.
Q13. How do you unit test a Spring service without starting the full application context?
Use plain JUnit 5 + Mockito — create @Mock objects for dependencies, @InjectMocks the real service class, and stub behavior with when()/thenReturn(). No Spring context is loaded at all, making these tests extremely fast.
Q14. What's the difference between @WebMvcTest and @SpringBootTest?
@WebMvcTest loads only the web/MVC layer (a "slice") for fast controller-focused testing with MockMvc, requiring @MockBean for service dependencies. @SpringBootTest loads the full real application context, suitable for true integration tests that need real bean wiring and database interaction (often paired with Testcontainers).
Q15. Why use Testcontainers instead of an in-memory database like H2 for tests?
H2 can behave subtly differently from your real production database (SQL dialect quirks, feature support gaps), hiding real bugs until production. Testcontainers spins up the actual database engine (e.g., real PostgreSQL) in a disposable Docker container per test run, giving much higher confidence the tests reflect real behavior.
Q16. How does Spring's caching abstraction work, and what's the danger of the default cache provider?
@Cacheable/@CachePut/@CacheEvict declaratively cache method results by key. The default Simple (ConcurrentHashMap) provider is per-JVM-instance — in a multi-replica deployment, each pod has its own separate cache, causing inconsistent results depending on which pod serves a request. Production multi-instance services must use a shared external cache like Redis.
Q17. What are real use cases for Redis beyond simple caching?
Rate limiting via atomic counters with TTL, session/token storage shared across instances, distributed locks (preventing duplicate concurrent processing across pods), sorted-set-based leaderboards, and lightweight Pub/Sub for ephemeral real-time notifications.
Q18. What is the difference between JPA and Hibernate?
JPA is a specification (interfaces/annotations like @Entity, EntityManager); Hibernate is a concrete implementation of that specification. Spring Boot's default underlying JPA implementation is Hibernate, but you're coding against the JPA API layer.
Q19. Why did the Java web stack evolve from Servlets → Struts → Spring → Spring Boot?
Each layer solved the previous layer's pain: Servlets enabled dynamic HTTP handling but mixed HTML and Java code; Struts added MVC structure but required heavy XML; Spring introduced lightweight DI to replace heavyweight EJB; Spring MVC added a cleaner web framework on Spring Core; Spring Boot eliminated remaining manual configuration via auto-configuration and embedded servers.
Q20. Describe a real production issue you've debugged involving Spring/Spring Boot and how you resolved it.
Example: a LazyInitializationException appeared intermittently in production when a controller tried to access a lazily-loaded JPA relationship after the transactional service method had already returned and closed the session. Fixed by mapping to DTOs entirely within the transactional service method boundary, ensuring all needed data is fetched while the session is still open.

58. Final Summary & Cheat Sheet

The journey: Core Java → Servlets/JSP (dynamic but messy) → JDBC (functional but boilerplate-heavy) → Hibernate/JPA (ORM solves mapping pain) → Spring Framework (lightweight DI replaces heavyweight EJB) → Spring MVC (clean web framework) → Spring Boot (auto-configuration, embedded servers, "just run it").

Spring Core: IoC container manages bean creation/wiring/lifecycle via Dependency Injection (prefer constructor injection), with AOP handling cross-cutting concerns declaratively.

Spring MVC: DispatcherServlet as Front Controller, routing through HandlerMapping to Controllers, rendering via ViewResolver (JSP/Thymeleaf) or returning JSON directly (@RestController).

Spring Boot: Auto-configuration + starters + embedded Tomcat eliminate nearly all manual setup; Profiles/YAML externalize environment-specific config; Actuator provides production-ready operational endpoints.

Transactions: @Transactional (via AOP proxies) manages atomicity within one database; Propagation controls nested transaction behavior; Isolation controls concurrent-transaction visibility; distributed operations across microservices use the Saga pattern instead of a single distributed transaction.

Testing: JUnit 5 + Mockito for fast isolated unit tests, MockMvc for controller-layer slice tests, @SpringBootTest + Testcontainers for true integration tests against real database/cache engines.

Caching/Redis: @Cacheable family for declarative caching; Redis as the mandatory shared backend for any multi-instance production deployment, also powering rate limiting, distributed locks, and session storage.
