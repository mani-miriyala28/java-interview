1. Before Git vs After Git

1.1 Life Before Version Control

Imagine a Java full stack team of 6 developers building an e-commerce app (Spring Boot backend + React frontend) without Git:

  • Developers email each other zip files like OrderService_final_v2_fixed.zip, OrderService_final_FINAL.zip.
  • Two developers edit OrderController.java at the same time; one overwrites the other's work.
  • There is no history — nobody knows who changed what, or why a bug was introduced.
  • To go back to yesterday's working version, someone must remember to keep a manual backup.
  • Deploying to production means manually copying files to a server — very risky and error prone.
  • Code review is done by reading printed code or screen-sharing — no structured process.
Real pain: A developer accidentally deletes a working application.yml config a day before release, and there is no way to recover it. The whole team stays late to rebuild it from memory.

1.2 Life After Git

  • Every change is tracked with an author, timestamp, and message — full history forever.
  • Multiple developers work on the same files in parallel using branches, without blocking each other.
  • Any file or the entire project can be restored to any previous point in seconds.
  • Code changes go through Pull Requests / Merge Requests with mandatory review and automated tests before reaching production.
  • Git works completely offline (it is distributed) — you can commit, view history, and branch without internet; you only need internet to push/pull to share with the team.
  • Combined with GitHub/GitLab/Bitbucket, it becomes a full collaboration and deployment platform: issues, CI/CD pipelines, code owners, security scanning, and release management.

1.3 What Git Actually Is

Git is a Distributed Version Control System (DVCS) created by Linus Torvalds in 2005. "Distributed" means every developer has a full copy of the entire project history on their own laptop — not just the latest files.

2. Git vs GitHub vs GitLab vs Bitbucket

Git has four conceptual areas a file moves through:

3.1 Real Example

# You edit OrderController.java in your IDE  → Working Directory
git add OrderController.java                 # → Staging Area
git commit -m "Add validation to order API"  # → Local Repository (.git)
git push origin feature/order-validation     # → Remote Repository (GitHub)

Each commit is identified by a unique SHA-1 hash (e.g., a3f5e21). Git stores commits as a linked chain — each commit points to its parent, forming the project history graph.

7. Understanding Branches

A branch is simply a movable pointer to a commit. Creating a branch is instant and cheap — this is what makes Git branching-friendly compared to older tools like SVN.

Branch = pointer to a commit
main
feature/x

Real example: a developer picks up JIRA ticket JIRA-231 to fix an order total bug.

git checkout develop
git pull origin develop
git switch -c feature/JIRA-231-order-total-fix
# ... edit OrderService.java, OrderServiceTest.java ...
git add .
git commit -m "JIRA-231: fix order total rounding bug"
git push -u origin feature/JIRA-231-order-total-fix
# then open a Pull Request / Merge Request into develop

8. Git Branching Strategies Used in Real Companies

8.1 Git Flow (used in regulated / release-based products, e.g., banking, insurance)

Git Flow
main
release/1.2
develop
feature/*
hotfix/*
  • main — always production-ready, tagged with version numbers.
  • develop — integration branch where finished features accumulate.
  • feature/* — one branch per ticket/feature, branched from develop, merged back to develop.
  • release/* — cut from develop when preparing a release, only bug fixes allowed, merged into both main and develop.
  • hotfix/* — cut from main to fix urgent production bugs, merged into both main and develop.
Real scenario: Production has a critical bug in payment rounding on a Friday evening. Team creates hotfix/payment-rounding from main, fixes it, tests it, merges to main (deployed immediately) AND to develop (so the fix isn't lost in the next release).

8.2 GitHub Flow (used in fast-moving SaaS/product teams with continuous deployment)

GitHub Flow — simple & continuous
main
(always deployable)
feature branch
→ PR + review + CI →
merge to main
→
auto-deploy

Only one long-lived branch: main. Every change is a short-lived feature branch merged via PR after review + passing CI, then deployed immediately (or automatically).

8.3 GitLab Flow (middle ground — environment branches)

Adds environment branches on top of GitHub Flow: main → pre-production → production, so each merge is promoted stage by stage instead of deploying straight to prod.

8.4 Trunk-Based Development (used by Google, Meta-scale teams, high maturity CI/CD)

  • Everyone commits to main (trunk) directly or via very short-lived branches (a few hours).
  • Unfinished features are hidden behind feature flags instead of long branches.
  • Requires strong automated testing and CI, since main is always deploying.

8.5 Which strategy for which real-world team?

Team typeRecommended strategyWhy
Banking/insurance, scheduled releasesGit FlowNeeds release branches, strict QA sign-off, hotfix path
SaaS product, deploys many times a dayGitHub FlowSimple, fast, PR + CI gate before merge
Enterprise with staged environmentsGitLab FlowClear promotion across dev → staging → prod
Large-scale, mature CI/CD, feature flagsTrunk-BasedAvoids long-lived branch merge pain at scale

8.6 Example: Real Java Full Stack Sprint Using Git Flow

# 1. Start feature from develop
git checkout develop && git pull
git switch -c feature/JIRA-410-add-cart-api

# 2. Work on backend (Spring Boot) + frontend (React) in same branch
git add backend/src/main/java/com/company/cart/CartController.java
git add frontend/src/components/Cart.jsx
git commit -m "JIRA-410: add cart REST API and Cart UI"

# 3. Push and open Pull/Merge Request into develop
git push -u origin feature/JIRA-410-add-cart-api

# 4. After 2 approvals + CI green -> squash merge into develop

# 5. Release day: cut release branch
git checkout develop && git pull
git switch -c release/1.4.0

# 6. QA finds a bug on release branch, fix directly there
git commit -m "fix: cart total tax calculation for release 1.4.0"

# 7. Release approved -> merge to main and tag
git checkout main && git merge --no-ff release/1.4.0
git tag -a v1.4.0 -m "Release 1.4.0"
git push origin main --tags

# 8. Merge back to develop so the fix is not lost
git checkout develop && git merge --no-ff release/1.4.0

9. Merge vs Rebase — Deep Dive

9.1 Merge

Combines two branch histories and creates a new "merge commit" with two parents. History is preserved exactly as it happened.

git merge feature into main
main
M
feature
git checkout main
git merge feature/JIRA-410-add-cart-api
# Creates a merge commit; both histories are kept, non-destructive

9.2 Rebase

Moves (replays) your branch commits on top of another branch's latest commit, producing a straight, linear history — as if you started your work after the latest change.

git rebase main (while on feature branch)
before
feature
after
git checkout feature/JIRA-410-add-cart-api
git fetch origin
git rebase origin/develop
# resolve conflicts if any, then:
git rebase --continue
git push --force-with-lease origin feature/JIRA-410-add-cart-api

9.3 When to use which (real team rules)

SituationUseReason
Merging a finished feature branch into develop/main via PRMerge (often squash merge)Keeps a clear "feature merged" point, safe for shared branches
Updating your own feature branch with latest develop before opening a PRRebaseClean linear history, easy to review, no noisy merge commits
Branch already pushed and others are using itMerge, not rebaseRebase rewrites history — dangerous for shared/public branches
Need very clean history for open-source projectRebase + squashOne clean commit per feature
Golden Rule: Never rebase a branch that other people are also working on / have already pulled — it rewrites commit hashes and breaks their history.

10. Git Cherry-Pick — Why and When

git cherry-pick takes one specific commit from one branch and applies it onto another branch, without merging the entire branch.

Cherry-pick one commit from release into main
release/1.4
✔
main
✔ copy

Why we use it (real reasons)

  • A critical hotfix commit exists on release/1.4 but must also go to main immediately, without pulling in unfinished release-branch changes.
  • You accidentally committed a small fix to the wrong branch and need it on the correct one.
  • Backporting a bug fix to an older supported version branch (e.g., release/1.3 still used by a client).
  • Picking a single useful commit from a colleague's experimental/abandoned branch.

Real scenario (Java full stack)

QA finds a critical NullPointerException in PaymentService.java already fixed on release/1.4 (commit 9af31bc), but main is already live in production and cannot take the whole unfinished release branch.

git log release/1.4 --oneline           # find the commit hash, e.g. 9af31bc
git checkout main
git pull origin main
git cherry-pick 9af31bc
# resolve conflicts if any
git push origin main
If cherry-picking a merge commit, use git cherry-pick -m 1 <hash> to tell Git which parent line to follow.

11. Git Stash — Saving Work in Progress

Stash temporarily shelves uncommitted changes so you can switch branches cleanly, then bring them back later.

Real scenario

You are mid-way through editing InventoryService.java for a new feature when your manager asks you to urgently fix a production bug on main.

git stash push -m "WIP: inventory reorder feature"
git checkout main
git pull
git switch -c hotfix/stock-count-bug
# fix, commit, push, PR ...
git checkout feature/inventory-reorder
git stash list
git stash pop      # restores your WIP changes

13. Handling Merge Conflicts — Step by Step

A conflict happens when Git cannot automatically decide how to combine changes because two branches edited the same lines differently.

Real example: two developers edit application.yml

<<<<<<< HEAD
server:
  port: 8080
=======
server:
  port: 9090
>>>>>>> feature/JIRA-512-new-port

Resolution steps

  1. git status — see which files are in conflict.
  2. Open each conflicted file, find the <<<<<<< / ======= / >>>>>>> markers.
  3. Decide the correct final content (talk to the other developer if unsure), delete the markers.
  4. git add <file> to mark it resolved.
  5. git commit (if merging) or git rebase --continue (if rebasing).
  6. Run tests locally before pushing.
Also common in Java projects: conflicts in pom.xml dependency versions, and in React projects: conflicts in package-lock.json — for lock files, usually safest to delete and regenerate with npm install after resolving package.json.

14. Tags & Release Management

Tags mark a specific commit as a release point, typically using Semantic Versioning: MAJOR.MINOR.PATCH (e.g., v2.3.1).

git tag -a v2.3.0 -m "Release 2.3.0 - Add cart and checkout APIs"
git push origin v2.3.0
git tag                     # list all tags
git checkout v2.3.0         # inspect exact code that was released

In GitHub/GitLab, tags are used to auto-trigger release pipelines that build a Docker image, e.g. myapp:2.3.0, and deploy it to production.

17. Working with Remotes — Fetch vs Pull, Forking

CommandBehavior
git fetchDownloads new commits from remote but does NOT touch your working files/branch
git pullgit fetch + git merge (or rebase, if configured) — updates your current branch immediately
Real time habit: Senior developers often prefer git fetch then review incoming changes (git log origin/main) before merging, especially on critical branches.

Forking workflow (common in open source and some enterprises)

  1. Fork the company/OSS repo into your own account.
  2. Clone your fork, add the original as upstream: git remote add upstream https://github.com/company/repo.git
  3. Create a feature branch, commit, push to your fork.
  4. Open a Pull Request from your fork's branch into the original repo.
  5. Periodically sync: git fetch upstream && git rebase upstream/main

20.2 Governance Controls Used by Real Organizations

23. Git Best Practices for Full Stack Teams

  • One feature/bugfix = one branch, named consistently: feature/JIRA-123-short-desc, hotfix/....
  • Small, frequent commits with clear messages (conventional commits: feat:, fix:, chore:, refactor:).
  • Always git pull --rebase or fetch+rebase before starting new work to avoid unnecessary merge commits.
  • Never commit secrets, credentials, or environment files.
  • Keep PRs/MRs small (< 400 lines changed where possible) — easier and faster to review.
  • Write meaningful PR descriptions: what changed, why, how tested, screenshots for UI.
  • Use draft PRs for work-in-progress visibility without triggering full review.
  • Protect main/develop with required reviews and passing CI.
  • Delete branches after merge to keep the repo clean.
  • Tag every production release for traceability and easy rollback.

25. Interview Questions & Answers

25.1 Basic Level

Q1. What is Git and why is it called "distributed"?
A: Git is a distributed version control system. Unlike centralized systems (SVN), every developer has a full copy of the repository including complete history on their local machine, so most operations (commit, branch, log, diff) work offline.
Q2. Difference between Git and GitHub?
A: Git is the version control tool itself. GitHub is a cloud platform that hosts Git repositories and adds collaboration features (Pull Requests, Issues, Actions/CI-CD, access control).
Q3. What is the difference between git fetch and git pull?
A: fetch downloads remote commits but does not change your working branch. pull = fetch + merge (or rebase), immediately updating your current branch.
Q4. What is the staging area (index)?
A: An intermediate area where changes are placed with git add before being permanently saved with git commit. It lets you commit only part of your changes.
Q5. What does .gitignore do?
A: Tells Git which files/folders to never track (e.g., target/, node_modules/, .env), keeping the repo clean and secrets safe.

25.2 Intermediate Level

Q6. Difference between merge and rebase?
A: Merge combines two histories with a new merge commit, preserving exact history (non-destructive). Rebase replays your commits on top of another branch, producing linear history but rewriting commit hashes (should not be done on shared/pushed branches).
Q7. What is cherry-pick and when do you use it?
A: Applies one specific commit from another branch onto the current branch. Used for backporting a hotfix to a release branch or main without merging the whole source branch.
Real world: A fix merged into develop is needed urgently in production; instead of merging all of develop (which has unfinished features), you cherry-pick just that one commit into main.
Q8. Difference between git reset and git revert?
A: reset moves the branch pointer and can rewrite/discard history (dangerous on shared branches). revert creates a brand-new commit that undoes changes, safe to use on shared/production branches because history isn't rewritten.
Q9. What is a detached HEAD state?
A: Happens when you checkout a specific commit or tag instead of a branch. Any new commits made there aren't attached to a branch and can be lost unless you create a new branch from that point.
Q10. What is git stash used for?
A: Temporarily saves uncommitted changes so you can switch branches cleanly (e.g., to handle an urgent hotfix), then restore your work later with git stash pop.
Q11. What is a fast-forward merge?
A: When the target branch has no new commits since the feature branch was created, Git simply moves the pointer forward instead of creating a merge commit.
Q12. What is git rebase -i (interactive rebase) used for?
A: To clean up local commit history before pushing/opening a PR — squash multiple small commits into one, reorder commits, edit or drop commits, fix commit messages.

25.3 Advanced / Scenario-Based (Real World)

Q13. Your PR has 15 messy "WIP" commits. How do you clean it up before review?
A: Use git rebase -i HEAD~15, mark commits to squash/fixup into one, write one clean commit message, then git push --force-with-lease (safe force push, only if branch is yours alone).
Q14. Production is broken from a bad merge to main. What do you do?
A: Prefer git revert <merge-commit-hash> -m 1 to safely create a new commit undoing the bad merge without rewriting shared history, then redeploy immediately. Avoid reset --hard + force-push on main.
Q15. Two developers changed the same lines in OrderService.java — how do you resolve on merge?
A: Git marks conflict with <<<<<<</=======/>>>>>>>. Discuss with the other developer, manually pick/combine the correct logic, remove markers, run tests, git add, then commit or continue the merge/rebase.
Q16. You need a fix from a colleague's still-unfinished branch, but not the whole branch. What do you do?
A: git cherry-pick <commit-hash> from their branch onto yours or into main, avoiding the unfinished parts.
Q17. What's the difference between Pull Request and Merge Request, and who typically approves them?
A: Same concept — GitHub/Bitbucket call it PR, GitLab calls it MR: a request to merge a branch after review. Approved by designated reviewers/code owners (per CODEOWNERS) plus required passing CI checks, enforced through branch protection rules; repo admins/maintainers can merge once conditions are met.
Q18. How do branch protection rules and CODEOWNERS work together at an organization level?
A: Branch protection defines the merge gate for a branch (min approvals, required CI checks, no force-push). CODEOWNERS maps specific paths (e.g. /payment/**) to required reviewers, so critical code always gets domain-expert review before it can merge.
Q19. You accidentally pushed an API key to a public repo. What now?
A: Immediately rotate/revoke the exposed key, remove it from history using git filter-repo or BFG Repo-Cleaner, force-push the cleaned history, and add the file to .gitignore. Rotating the credential is the most important step — history rewrite alone is not enough since it may already be cached/forked.
Q20. Difference between Git Flow and Trunk-Based Development — when would you pick each?
A: Git Flow uses long-lived develop/release/hotfix branches, good for scheduled releases (banking, enterprise). Trunk-based development commits frequently to main using short branches and feature flags, suited to teams with strong CI/CD and multiple daily deployments (e.g., SaaS/product companies).
Q21. How would you set up Git so backend and frontend teams don't block each other, but still integrate smoothly?
A: Separate feature branches per ticket for each team, merged into a shared develop branch through PRs/MRs gated by CI (backend runs mvn test, frontend runs npm test), with an integration environment auto-deployed from develop for cross-team testing before release.
Q22. What is git bisect and when have you used it?
A: A binary-search tool to find which commit introduced a bug by marking known good/bad commits; Git automatically checks out midpoints until the exact breaking commit is found. Useful in real projects to trace regressions across hundreds of commits quickly.
