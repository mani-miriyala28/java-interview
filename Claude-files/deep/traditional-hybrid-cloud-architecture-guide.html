1. Introduction — Traditional, Hybrid and Full Cloud at a Glance

1.1 The Three Architecture Models This Guide Covers

Three Deployment Models — At a Glance

Everything in your own data center
Hybrid

1.2 Why Understanding All Three Matters

Very few real organizations jump straight from "nothing" to "100% cloud-native" — most walk through all three stages over years, and many large enterprises (banks, insurance, government) still run significant Hybrid architectures today for regulatory, legacy, or cost reasons. Understanding all three — and how to move between them — is essential real-world architecture knowledge, not just a historical curiosity.

Every single box in the diagram above is a PHYSICAL (or virtualized-on-physical) server sitting in the organization's own data center (or a rented colocation facility) — owned or leased hardware, racked, cabled, powered, and cooled by the organization's own infrastructure team, with no cloud provider involved anywhere in this picture.

4.1 The Complete Journey of One Real Request

On-Premises Request — Full Internal Flow
1. User's browser sends HTTPS request to the company's public-facing domain
↓ DNS resolves to the data center's public IP (Web/Network Basics guide, Section 2.2)
2. Corporate Firewall inspects and allows the traffic through
↓
3. F5/Nginx Load Balancer terminates TLS, picks a healthy web server
↓
4. React UI's static files are served (or, for API calls, forwarded onward)
↓
5. On-prem API Gateway authenticates the request, routes based on path
↓
6a. User Service (Spring Boot) handles /users/*
6b. Order Service (Spring Boot) handles /orders/*
↓
7. Service queries Oracle/DB2 over the internal network (private VLAN)
↓ if the action triggers a downstream event

↓

9b. Notification Service consumes and triggers Email/SMS
↓

4.2 What Happens INSIDE the Spring Boot Service at Step 6-7 (Recap)

Exactly the same internal Spring Boot request lifecycle already covered in complete depth in the Web/Network/Startup/Redis guide (Section 21) — DispatcherServlet, HandlerMapping, Controller, @Transactional Service layer, Repository/JPA/Hibernate hitting the database — this lifecycle is IDENTICAL regardless of whether the service happens to be running on-premises or in the cloud; only the surrounding infrastructure differs.

5. On-Premises Deployment Flow (Git → Jenkins → Docker → Servers)

5.1 The Real Deployment Pipeline

On-Premises CI/CD Flow
Git (self-hosted GitLab/Bitbucket, or GitHub Enterprise)
→
Jenkins (self-hosted CI server)
↓ build, test, package
Docker Build (on a Jenkins agent, or a dedicated build server)
↓ push to a self-hosted private registry (e.g., Nexus, Harbor)
Deploy to Servers (via Ansible/shell scripts, or manual runbook steps)

5.2 What Actually Happens at Each Stage

  1. Git: developer pushes code to a self-hosted Git server (no cloud-hosted GitHub/Azure Repos dependency in a fully on-prem shop).
  2. Jenkins: a webhook or polling trigger kicks off a pipeline job — compiles, runs unit tests, and often SonarQube (self-hosted) quality gates.
  3. Docker Build: Jenkins agent builds the Docker image on its own hardware, tags it, pushes to a self-hosted private registry.
  4. Deploy to Servers: a deployment script (often Ansible, or in less mature setups, a manual SSH-and-run-script process) pulls the new image and restarts the service on each target server.

5.3 Real Limitations of This Pipeline (Motivating Later Cloud Adoption)

LimitationReal Impact
Jenkins itself needs its own dedicated server(s) to maintain, patch, and scaleAdditional infrastructure burden on top of the application infrastructure itself
No elastic build capacityA surge of concurrent builds queues up, waiting for available Jenkins agents
Manual/scripted deployment to a FIXED set of serversNo true auto-scaling of the deployment target itself — capacity is whatever's physically racked
Rollback often means manually redeploying a previous versionSlower, more error-prone recovery compared to Kubernetes' instant rollout undo (Docker & Kubernetes guide, Section 21.4)

8. What Is Hybrid Cloud and Why Organizations Use It

8.1 The Core Definition

Hybrid Cloud means running SOME workloads on-premises and OTHERS in a public cloud (Azure/AWS), with the two environments connected and working together — not a "migration in progress" necessarily, but often a deliberate, long-term architectural choice.

8.2 Real Reasons Organizations Choose (or Stay) Hybrid

ReasonReal Example
Regulatory/data-residency requirementsCore ledger/customer PII data must legally remain on-premises in a specific jurisdiction
Legacy system dependenciesA mainframe or DB2 system too costly/risky to migrate, but new services should be cloud-native
Gradual migration strategyMoving one service at a time to the cloud (Strangler Fig pattern, Microservices guide Section 9) while the rest stays on-prem
Burst capacity ("cloud bursting")Core capacity stays on-prem (already paid for), but traffic SPIKES burst into the cloud temporarily
Existing capital investmentRecently purchased expensive on-prem hardware not yet fully depreciated

8.3 Hybrid Cloud vs "Cloud Migration in Progress" — An Important Distinction

Sometimes Hybrid is a permanent, deliberate end-state (e.g., regulatory data residency), and sometimes it's a temporary transitional phase during an active migration (Sections 20-22) — real architecture decisions must be clear about WHICH of these two scenarios actually applies, since the two call for very different levels of investment in the hybrid connectivity itself.

9.2 Common Real Hybrid Split Patterns

Dev/Test-Cloud, Prod-On-PremProduction workloadsDevelopment and testing environmentsGet elastic, low-cost dev/test capacity while production stability requirements are met on proven on-prem infrastructure
Burst-to-CloudBaseline/steady-state capacityOverflow capacity during traffic spikesAvoid over-provisioning on-prem hardware for rare peak events (Black Friday-style)
DR (Disaster Recovery)-in-CloudPrimary productionA cloud-hosted disaster recovery replicaCheaper and faster than building/maintaining a second physical data center

9.3 Real Data Synchronization Challenges

Whenever data or services span both environments, keeping them consistent becomes a real engineering challenge — network latency between on-prem and cloud (even over a dedicated ExpressRoute link) is inherently higher than within a single environment, and any service calling across that boundary must apply the full resilience pattern set (timeout, retry, circuit breaker — Microservices guide Section 40) even more rigorously than for purely intra-cloud calls.

Real hybrid organizations typically federate their on-premises Active Directory with Azure Entra ID (Entra ID Connect / Azure AD Connect) — one single identity works seamlessly across BOTH environments, rather than maintaining two entirely separate, disconnected identity systems.

12. Hybrid Cloud Real Scenarios & Migration Considerations

12.1 Real Scenario — Phased Migration Using Hybrid as a Stepping Stone

"Our organization moved the React frontend and stateless API layer to Azure FIRST (low risk, immediate user experience/performance benefit via Front Door's global CDN), while the core ledger database stayed on-premises for another 18 months while the DBA team carefully planned and executed its own migration (Sections 20-22) — this phased Hybrid approach let us deliver real, immediate value to users without waiting for the hardest, highest-risk part of the migration (the core database) to be ready."

12.2 Real Scenario — Permanent Regulatory Hybrid

"A healthcare/financial client's core PII database remains PERMANENTLY on-premises due to strict data-residency regulation in their jurisdiction — this isn't a migration-in-progress, it's the organization's deliberate, permanent target architecture, with the cloud used for everything that ISN'T subject to that specific regulatory constraint."

12.3 Key Decision Factors for Choosing (or Staying) Hybrid

  • Regulatory/compliance requirements mandating specific data stay within a jurisdiction or specific physical control.
  • Existing capital investment in on-prem hardware not yet depreciated.
  • Legacy system migration risk/cost genuinely outweighing the benefit of moving it, at least for now.
  • Organizational readiness/skills — a gradual hybrid transition lets teams build cloud expertise incrementally rather than all at once.

14. Where React, Backend and Database Actually Get Deployed in Full Cloud

14.1 React Frontend — Deployment Location

React's built static bundle (HTML/CSS/JS, produced once via npm run build) is deployed to Azure Static Web Apps — a service specifically designed to host static frontend content, with built-in global CDN distribution, automatic HTTPS, and direct GitHub/Azure DevOps integration for automatic deployment on every push.
# Real Azure Static Web App deployment via Azure DevOps/GitHub Actions
- task: AzureStaticWebApp@0
  inputs:
    app_location: "/customer-portal"
    output_location: "build"
    azure_static_web_apps_api_token: $(deployment_token)

14.2 Spring Boot Backend — Deployment Location

Every Spring Boot microservice (User MS, Order MS, Payment MS) is containerized (Docker & Kubernetes guide, full detail) and deployed as its own Kubernetes Deployment/Pods running inside AKS (Azure Kubernetes Service) — each with its own Service, HPA, and resource limits, exactly per the Microservices guide's real organizational pattern.

↓ if the action triggers a downstream event

↓ consumed independently, asynchronously, NOT blocking this request's response
Inventory Service
Notification Service
Audit Service
↓ meanwhile, Order MS's response is already flowing back

↓ throughout this ENTIRE flow

16. Full Cloud Security (Key Vault, Entra ID)

16.1 Key Vault — Full Recap in This Architecture's Context

Every single secret used anywhere in this architecture — database connection strings, JWT signing keys, third-party API keys, TLS certificates — is stored in Azure Key Vault, never hardcoded, accessed via Managed Identity (AWS/Azure guide, Section 9.5) with zero credentials ever appearing in code, config files, or CI/CD variables in plaintext.

16.2 Entra ID — Identity for Both Humans and Applications

Identity TypeReal Use in This Architecture
Human users (customers)Authenticate via Entra ID B2C (or a custom identity flow), receive a JWT used for every API call
Human users (developers/admins)Authenticate to the Azure Portal, AKS, and Azure DevOps via their corporate Entra ID account
Applications (Spring Boot services)Each AKS pod uses a Managed Identity, granted least-privilege RBAC roles (AWS/Azure guide, Section 9.3) to access Key Vault, Cosmos DB, etc.

16.3 Full Defense-in-Depth Security Layering in This Architecture

↓

21.2 Step 1 — Assess & Discover

Inventory every application, its dependencies, data flows, and current resource utilization — real organizations use tools like Azure Migrate to automatically discover on-premises VMs/servers and assess their cloud readiness and estimated cost.

21.3 Step 2 — Plan & Choose Strategy Per Workload

Apply the 6 R's (Section 20) to EACH individual application/service — not a single blanket decision for the whole organization.

21.4 Step 3 — Design Target Azure Architecture

21.5 Step 4 — Build Landing Zone

Establish the foundational Azure infrastructure BEFORE migrating any workload — VNets/subnets (AWS/Azure guide, Section 8), Entra ID setup, RBAC policies, Key Vault, and governance/cost-management guardrails — a stable, secure foundation everything else builds on top of.

Run the new cloud environment in PARALLEL with the old on-premises system where possible (exactly the Strangler Fig pattern, Microservices guide Section 9), gradually shifting real traffic over (often via DNS weighting or a router splitting traffic by percentage) rather than an instant, risky "big bang" cutover.

Once the cloud environment is proven stable under real production load, decommission the old on-premises infrastructure (or repurpose it), and begin ongoing cost/performance optimization — cloud migration isn't a one-time event, it's followed by continuous tuning (right-sizing VMs, adjusting auto-scaling thresholds, reviewing storage tiers).

23. What Happens When You Open a URL — Basic Introduction With a Real Example

23.1 The Simple Version, In Plain Language

Let's use a real example: you open your banking app and type app.mybank.com. In the simplest possible terms — your browser finds the bank's server on the internet, asks it for the login page, the server sends it back, and your browser displays it. Everything else in this guide is really just filling in the details of exactly HOW that happens.

23.2 The Real Basic Flow

Basic Flow — Opening app.mybank.com
You type app.mybank.com and press Enter
↓
Your browser finds the bank's server's address (DNS)
↓
Your browser asks that server: "give me the login page"
↓
The bank's server sends back the page's content
↓
Your browser draws it on your screen

23.3 What Happens When You Then Click "View My Balance"

Basic Flow — Clicking "View My Balance"
You click the button
↓
The React app (already loaded in your browser) sends a small request asking for YOUR account balance specifically
↓
The bank's backend checks who you are (your login token), looks up your balance in the database

This second flow — clicking a button and getting just a small piece of data back, without reloading the whole page — is exactly how modern React Single Page Applications work, and it's the foundation for the fully detailed, technical version of this same flow in Section 24.

24. What Happens When You Open a URL — Full Advanced Internal Working

24.1 The Complete Technical Journey, Every Layer

Full Advanced Flow — app.mybank.com, "View My Balance"
1. Browser checks its local DNS cache; if empty, queries a DNS resolver (often your ISP's or a public one like 1.1.1.1)
↓
2. DNS resolver returns the IP address of Azure Front Door's nearest edge location to you, geographically
↓
3. Browser opens a TCP connection to that IP on port 443 (three-way handshake: SYN, SYN-ACK, ACK)
↓
4. TLS handshake: browser and Front Door edge agree on encryption, Front Door proves its identity via its TLS certificate
↓ connection is now encrypted
5. Browser sends the actual HTTP GET request (encrypted) for the page/app shell
↓
6. Front Door checks its edge cache — the React app's static files are cached here, served INSTANTLY without going anywhere else
↓ React app now runs in your browser, renders the login/dashboard UI
7. You click "View My Balance" — React's JavaScript code constructs an API call: GET /api/v1/accounts/1001/balance
↓ this request includes your stored JWT token in the Authorization header
8. This request is NOT cacheable (personalized data) — Front Door forwards it to Azure API Management
↓
9. APIM verifies the JWT's signature against Entra ID's public key, checks it hasn't expired
↓ valid
10. APIM checks your rate limit hasn't been exceeded, then forwards the request to AKS Ingress
↓
11. AKS Ingress Controller matches the URL path to the Accounts Service's Kubernetes Service
↓
12. Kubernetes Service picks one healthy Accounts Service pod (kube-proxy load balancing)
↓ INSIDE that pod now
13. Linux kernel's network stack delivers the packet to the JVM process listening on its port
↓
14. Embedded Tomcat's connector accepts the connection, hands it to a worker thread from its thread pool
↓
15. Servlet Filter Chain runs: CORS filter → correlation ID filter (tags this request for tracing) → Spring Security filter (re-validates the JWT at the application level too — defense in depth)
↓
16. DispatcherServlet (Front Controller) receives the request
↓
17. HandlerMapping matches GET /accounts/{id}/balance to AccountController.getBalance()
↓
18. Controller calls AccountService.getBalance(id) — a @Transactional method begins
↓
19. Service layer checks Redis Cache FIRST for this account's balance (cache-aside pattern)
↓ CACHE MISS (balance changed recently, TTL expired)
20. Repository (Spring Data JPA) generates and executes SQL against Azure SQL Database via the connection pool (HikariCP)
↓
21. Azure SQL Database's own storage engine reads the data from its (mostly memory-cached) storage, returns the row
↓
22. Hibernate maps the ResultSet to an Account entity object; Service maps it to an AccountDto; the result is written into Redis Cache for next time
↓ transaction commits
23. Controller returns the DTO; Jackson serializes it to JSON
↓
24. Response flows back OUT through the same filter chain, then the pod, Ingress, APIM, Front Door, and finally to your browser
↓
25. React receives the JSON, updates its component state, re-renders JUST the balance display on your screen
↓ throughout ALL 24 steps above
26. Application Insights recorded a distributed trace span at every single hop, all tagged with one shared trace ID, viewable as a single connected timeline

24.2 Total Real-World Elapsed Time

Despite this being 26 distinct conceptual steps across many different systems, the ENTIRE flow — from your click to seeing your updated balance — typically completes in well under 200 milliseconds in a healthy, well-architected system, often under 100ms on a cache hit. Understanding this full depth is exactly what separates "I can write a Spring Boot controller" from "I understand how my code actually reaches a real user, end to end, in production."

25. Interview Questions & Real-Time Scenario-Based Q&A

Q1. What are the three main deployment models covered in this guide, and how do they fundamentally differ?
Traditional On-Premises (everything self-hosted in your own data center), Hybrid (some workloads on-prem, some in the cloud, connected via VPN/ExpressRoute), and Full Cloud-Native (everything hosted and managed by a cloud provider like Azure). They differ primarily in who owns/manages infrastructure, cost model (fixed capital vs pay-as-you-go), and scaling flexibility.
Q2. Why might a large regulated organization deliberately choose to remain Hybrid rather than fully migrating to the cloud?
Regulatory/data-residency requirements mandating certain data remain within a specific physical jurisdiction or under direct organizational control, existing capital investment in on-prem hardware, or genuine legacy system migration risk/cost — Hybrid can be either a permanent deliberate architecture or a temporary transitional phase.
Q3. What's the real difference between a Site-to-Site VPN and Azure ExpressRoute for hybrid connectivity?
A Site-to-Site VPN is an encrypted tunnel over the public internet — cheaper but subject to variable latency/congestion. ExpressRoute is a dedicated, private physical circuit directly into Azure, never touching the public internet — more expensive, but far more predictable latency and stronger security/compliance posture.
Q4. Explain the 6 R's of cloud migration strategy with a real example of when you'd use each.
Rehost (lift-and-shift a low-priority app as-is), Replatform (move to a managed service like App Service with minor changes), Repurchase (replace with a SaaS alternative), Refactor (re-architect into cloud-native microservices for long-term agility), Retire (decommission unused applications), and Retain (deliberately keep something on-premises, e.g., due to regulation).
Real scenario: applying Rehost to a low-priority internal tool, Refactor to core customer-facing services, Retire to unused reporting tools, and Retain for a regulated core database — all within one migration program.
Q5. Why do real migrations use a phased "wave" approach instead of migrating everything at once?
A pilot wave with a low-risk application validates the process and builds team confidence/skills with minimal business risk; low-risk workloads follow next; core/critical systems are migrated last, once the team has real, proven experience — avoiding the high risk of a single "big bang" migration of everything simultaneously.
Q6. What real cost differences exist between Traditional On-Premises and Full Cloud-Native models?
On-premises requires very high upfront capital cost (buying hardware for peak capacity that mostly sits idle) with predictable fixed ongoing costs regardless of actual usage. Full Cloud-Native has minimal upfront cost and fully variable, usage-based pricing, which can be cheaper overall but requires active cost governance to avoid unexpected spend from unused/over-provisioned resources.
Q7. Walk through what happens, in full technical detail, when a user clicks a button in a React app that calls a backend API.
React's JavaScript constructs an API call including the stored JWT token; if not cacheable, it's forwarded through the CDN/Front Door to the API Gateway/APIM, which validates the JWT and applies rate limiting, then routes through the Kubernetes Ingress to a load-balanced Service, into a specific Spring Boot pod, through its filter chain (security, correlation ID), DispatcherServlet, Controller, a @Transactional Service layer (checking cache first), Repository/JPA hitting the database on a cache miss, and the response flows back out through the exact same path, all captured end to end by a single distributed trace ID.
Q8. Why is defense-in-depth security important across this full request flow, rather than relying on just one layer?
Each layer (WAF at the edge, JWT validation at the API Gateway, network policies within Kubernetes, Spring Security within the application, database-level access control) provides independent protection — if any single layer is misconfigured or bypassed, the others still provide protection, rather than the entire system's security depending on one single point of failure.
Q9. What's the real difference in observability/monitoring maintenance burden between On-Premises and Full Cloud models?
On-premises requires your own team to install, patch, scale, and ensure high availability of the observability stack itself (Splunk, Grafana, Zipkin servers) — the monitoring tools themselves need monitoring. In Full Cloud, Azure Monitor/Application Insights are fully managed services requiring no infrastructure maintenance from your team at all.
Q10. Describe a real scenario where a migration project ran into unexpected performance problems, and how you'd diagnose/fix it.
A "lift and shift" migration performed worse in the cloud than on-premises because the VM sizing and network topology weren't adjusted for the cloud environment's actual characteristics. Diagnosed via real observed CPU/memory/network metrics post-migration, then fixed by right-sizing resources and considering a Replatform pass (e.g., moving to a managed PaaS service) rather than assuming a pure like-for-like VM migration would automatically perform equivalently.
Q11. Why would an organization keep its core database on-premises while moving its frontend and API layer to the cloud (as in the Hybrid example)?
This "Frontend-Cloud, Data-On-Prem" pattern delivers immediate, lower-risk user experience improvements (global CDN, elastic API scaling) without needing to solve the much harder, higher-risk problem of migrating a critical, deeply embedded legacy database — the database migration can proceed carefully and separately, on its own timeline.
Q12. What real latency consideration must a service account for when calling across a Hybrid boundary (cloud to on-premises)?
Every call crossing the ExpressRoute/VPN boundary pays a real, measurable round-trip cost higher than intra-cloud or intra-datacenter calls — real teams mitigate this by caching frequently-accessed, rarely-changing reference data locally (e.g., in Redis within the cloud environment) to avoid unnecessarily crossing that boundary on every single request.

26. Final Summary & Cheat Sheet

Traditional On-Premises: full control, predictable fixed costs, but high operational burden, slow scaling, poor global reach, and every layer (network, hardware, OS, observability tooling) is your own team's responsibility.

Hybrid: a deliberate or transitional split between on-prem and cloud, connected via VPN/ExpressRoute, driven by regulatory constraints, legacy dependencies, or as a genuine phased migration path — with real added latency and complexity at the boundary that must be actively managed.

Full Cloud-Native: React on Azure Static Web Apps, Spring Boot microservices on AKS, databases as managed Azure SQL/Cosmos DB/Redis services, all secured via Key Vault/Entra ID, observed via Azure Monitor/Application Insights, and delivered continuously via Azure DevOps/ACR/AKS — elastic, globally reachable, with infrastructure maintenance burden largely shifted to the cloud provider.

The full request lifecycle: from DNS resolution and TLS handshake, through CDN edge caching, API Gateway authentication/rate-limiting, Kubernetes routing, the complete internal Spring Boot request pipeline (filters → DispatcherServlet → Controller → Service → cache-aside → Repository/database), all the way back to the user's screen — typically completing in well under 200ms, entirely traced end to end by a single correlation ID.

Migration: apply the 6 R's per-workload (not uniformly), build a solid landing zone first, migrate in waves starting with low-risk pilots, validate via parallel running before cutover, and treat optimization as continuous, not a one-time event.
