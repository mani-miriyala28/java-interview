1. Before Docker — Traditional Servers, VMs and Their Problems

1.1 Era 1 — Physical/Traditional Servers

Before virtualization, every application ran on its own physical machine bought, racked, and cabled in a data center. If you had 5 applications, you bought and maintained 5 physical servers.
Traditional Physical Server Era
Physical Server 1
App A + full OS
Physical Server 2
App B + full OS
Physical Server 3
App C + full OS
  • Problem 1 — Massive waste: each server used maybe 10-15% of its CPU/RAM capacity, but you still paid for 100% of the hardware.
  • Problem 2 — Slow provisioning: ordering, racking, and configuring a new physical server took days to weeks.
  • Problem 3 — No isolation flexibility: one app crashing the OS could take the whole physical box down.
  • Problem 4 — Scaling was physical: "scale up" meant literally buying more hardware.

1.2 Era 2 — Virtual Machines (VMware, Hyper-V, KVM)

Virtualization let one physical server run multiple Virtual Machines, each with its own full guest OS, via a hypervisor. This solved the "one app per box" waste problem.
Virtual Machine Era
Physical Server (Host)
↓ Hypervisor (VMware/Hyper-V)
VM 1
Guest OS + App A
VM 2
Guest OS + App B
VM 3
Guest OS + App C
  • Better: much higher hardware utilization, isolated environments, snapshots/backups became easy.
  • Still a Problem 1 — Heavy: every VM carries a full guest operating system (kernel + libraries), often several GB, and takes minutes to boot.
  • Still a Problem 2 — Resource overhead: running 10 VMs means 10 full OS kernels consuming CPU/RAM just for the OS itself, not the app.
  • Still a Problem 3 — "Works on my machine": a developer's laptop, the QA VM, and the production VM often had subtly different OS patches, library versions, or configs — causing bugs that only appeared in one environment.
  • Still a Problem 4 — Slow CI/CD: spinning up a new VM for testing was slow (minutes), which slowed down automated pipelines.

1.3 What Java/Spring Boot Teams Actually Faced (Real Story)

A typical pre-container Java shop had: a shared Tomcat server with multiple WARs deployed on it, an ops team manually copying WAR files via FTP/SCP, an ops-checklist.docx describing 20 manual steps to prepare a new environment, and constant "which JDK/library version is on this server?" confusion between Dev, QA and Prod.
Real scenario: "Our order-service used Java 8 update 202 in production, but a new VM provisioned for a scale-out event had Java 8 update 265 installed by default — a subtle date-parsing bug that only reproduced on the newer patch version caused an outage. This was purely an environment inconsistency problem — the exact class of issue containers were built to solve."

2. Why Docker Came — The Real-World Story

2.1 The Core Idea Docker Introduced (2013)

Instead of virtualizing an entire computer (like a VM), Docker virtualizes at the operating system level — many containers share the same host OS kernel, but each is isolated with its own filesystem, process space, and network. No guest OS needed per app.
VM vs Container — Side by Side
Host OS + Hypervisor
VM: Guest OS + Libs + App (GBs, slow boot)
— vs —
Host OS + Docker Engine
Container: Libs + App only (MBs, boots in seconds)
Container: Libs + App only (MBs, boots in seconds)

2.2 What Problems Docker Actually Solved

Old ProblemHow Docker Solves It
"Works on my machine" bugsThe exact same image (app + dependencies + runtime) runs identically on laptop, QA, and Prod
Heavy VMs, slow bootContainers share the host kernel — start in seconds, images are typically MBs not GBs
Manual environment setupDockerfile codifies the entire environment as version-controlled text
Low server densityYou can run dozens of containers on a host that could only fit a few VMs
Slow CI/CD feedbackSpinning up a container for a test job takes seconds, enabling fast pipelines
Dependency hell (conflicting library versions)Each container has its own isolated filesystem/dependencies, no clashes between apps on the same host

2.3 From a Spring Boot Perspective

Spring Boot already bundles an embedded Tomcat/Jetty into a single executable JAR — this made it a perfect fit for containers: java -jar app.jar inside a small JRE-based image is basically the entire deployment story. No external application server to install/configure on the host anymore.

2.4 From a React Perspective

React builds into static HTML/CSS/JS files. Before Docker, these were manually copied to a web server (Apache/Nginx/IIS) with environment-specific config. With Docker, the build output + a minimal Nginx server are packaged into one small image that behaves identically everywhere.

2.5 The Container Philosophy (Simple Terms)

  • Build once, run anywhere — a Docker image is a single portable unit.
  • Immutable artifacts — you don't patch a running container, you replace it with a new image version.
  • Declarative environment — the Dockerfile is the single source of truth for what's inside.
  • Process isolation, not full OS duplication — lightweight compared to VMs.
Interview one-liner: "Docker solves environment inconsistency and heavy resource usage by packaging an app with its exact dependencies into a lightweight, portable container that shares the host OS kernel instead of duplicating a full guest OS like a VM does."

3. Docker Core Concepts (Image, Container, Registry, Layers)

3.1 The Four Building Blocks

Docker Core Concepts Flow
Dockerfile (recipe)
→
Image (built, read-only template)
→
Container (running instance of image)
↓ push / pull
Registry (Docker Hub / ACR / ECR / GitLab Registry)

3.2 Dockerfile

A plain text file with step-by-step instructions to build an image — base OS/runtime, files to copy, dependencies to install, command to run.

3.3 Image

The built, immutable, read-only template made of stacked layers. An image is not running — it's a snapshot ready to be started as a container. Identified by name:tag, e.g., order-service:1.4.2.

3.4 Container

A running (or stopped) instance of an image, with a thin writable layer on top for runtime changes. You can run many containers from the same image, each isolated from the others.

3.5 Registry

A storage/distribution service for images. Examples: Docker Hub (public), Azure Container Registry (ACR), Amazon ECR, GitLab Container Registry, self-hosted Harbor/Nexus.

3.6 Image Layers Explained

Every instruction in a Dockerfile (FROM, RUN, COPY, etc.) creates a new, cached layer. Layers are stacked and shared across images — if two images both start FROM eclipse-temurin:17-jre, that base layer is downloaded/stored only once on a host.
Image Layer Stack (Spring Boot Example)
Layer 1: Base OS (Alpine Linux)
Layer 2: JRE 17 runtime
Layer 3: WORKDIR + app user setup
Layer 4: COPY app.jar
Thin writable layer (only exists once container runs)
Why this matters: Docker caches each layer. If you only change your application code (last COPY layer) and not your dependencies, rebuilding reuses all earlier cached layers — massively speeding up builds. This is why Dockerfile instruction order matters (see Section 6).

Docker containers need a Linux kernel. On Windows/Mac, Docker Desktop runs a lightweight Linux VM (via WSL2 on Windows, or a hypervisor on Mac) under the hood, and your containers actually run inside that VM — this is why Docker Desktop asks you to enable WSL2/Hyper-V.

5. Installing & Setting Up Docker (Real Steps)

5.1 Local Developer Machine Setup

  1. Install Docker Desktop (Windows/Mac) or Docker Engine directly (Linux).
  2. On Windows: enable WSL2 backend for better performance than the legacy Hyper-V backend.
  3. Verify installation: docker --version and docker run hello-world.
  4. Log in to your organization's registry: docker login myregistry.azurecr.io.

5.2 Real Organization Server/Build-Agent Setup

  • CI/CD build agents (Jenkins agent, Azure Pipelines self-hosted agent) have Docker Engine pre-installed so pipeline steps can run docker build/docker push.
  • Production Kubernetes nodes use a container runtime (containerd, historically Docker Engine, now often containerd directly per Kubernetes' removal of "dockershim").
  • Registries are private (ACR/ECR/Harbor) with role-based access — only CI/CD service principals and admins can push.

5.3 First Commands to Sanity-Check Everything

docker --version                     # confirms Docker CLI is installed
docker info                          # shows daemon status, storage driver, resource info
docker run hello-world               # pulls a tiny test image and confirms daemon works end-to-end
docker images                        # lists locally stored images
docker ps                            # lists running containers

6. Dockerfile Deep Dive — Every Instruction Explained

6.1 A Complete Annotated Dockerfile

# Stage 1: Build (only needed to compile, not shipped in final image)
FROM maven:3.9-eclipse-temurin-17 AS build      # base image with Maven + JDK 17
WORKDIR /app                                     # sets working directory inside the image
COPY pom.xml .                                   # copy pom.xml first (for dependency layer caching)
RUN mvn dependency:go-offline                    # pre-download deps — cached unless pom.xml changes
COPY src ./src                                   # now copy source code (changes most often)
RUN mvn clean package -DskipTests                # compile and package into a JAR

# Stage 2: Runtime (this is what actually ships to production — small!)
FROM eclipse-temurin:17-jre-alpine               # minimal JRE-only base image (no Maven, no JDK)
RUN addgroup -S app && adduser -S app -G app     # create a non-root user (security best practice)
WORKDIR /app
COPY --from=build /app/target/*.jar app.jar      # copy only the built JAR from Stage 1
USER app                                         # run container as non-root
EXPOSE 8080                                      # documents the port the app listens on
ENV SPRING_PROFILES_ACTIVE=prod                  # default environment variable
HEALTHCHECK --interval=30s --timeout=3s CMD wget -qO- http://localhost:8080/actuator/health || exit 1
ENTRYPOINT ["java", "-jar", "app.jar"]            # fixed command that always runs

6.2 Every Instruction Explained

InstructionWhat It Does
FROMChooses the base image to start from — every Dockerfile must start with this (or ARG before it)
WORKDIRSets/creates the working directory for subsequent instructions — avoids messy absolute paths
COPYCopies files from build context (your machine/CI) into the image
ADDLike COPY but also supports remote URLs and auto-extracting tar archives — generally COPY is preferred unless you need those extras
RUNExecutes a command at build time, result is committed as a new layer (e.g., installing packages, compiling code)
ENVSets an environment variable available at build and container run time
ARGA build-time-only variable (not available in the running container unless also set as ENV)
EXPOSEDocuments which port the container listens on (does not actually publish it — that's -p on docker run)
USERSwitches the user the rest of the instructions/container run as — critical for security (avoid root)
CMDDefault command/arguments if none given at docker run — can be overridden
ENTRYPOINTThe fixed main command that always runs — harder to override, often combined with CMD for default args
HEALTHCHECKTells Docker how to test if the container is actually healthy, not just "running"
VOLUMEMarks a directory as a mount point for persistent/external storage
LABELAdds metadata (maintainer, version, git commit hash) to the image

6.3 CMD vs ENTRYPOINT — The Classic Confusion

CMDENTRYPOINT
Overridable?Yes, easily replaced by docker run image other-commandNo (unless --entrypoint flag used) — meant to be fixed
Typical useDefault argumentsThe actual program that must always run
Best patternCombine both: ENTRYPOINT ["java","-jar","app.jar"] with optional CMD ["--spring.profiles.active=dev"] as default overridable args

6.4 Dockerfile Instruction Order Matters (Build Speed)

Put things that change least often (base image, dependency manifests) at the top, and things that change most often (your source code) at the bottom. This maximizes Docker's layer cache reuse and dramatically speeds up rebuilds — this is why COPY pom.xml happens before COPY src in the example above.

7. How Many Images Can You Create From One Dockerfile? (Tags, Layers, Multi-Stage)

7.1 One Dockerfile → Unlimited Images (via Tags)

A Dockerfile is just a build recipe. Every time you run docker build, you can tag the result differently — so a single Dockerfile can produce as many distinct, independently stored images as you want, each identified by its own name:tag.
docker build -t order-service:1.0.0 .
docker build -t order-service:1.0.1 .
docker build -t order-service:latest .
docker build --build-arg APP_ENV=qa -t order-service:qa-1.0.0 .
  • Same Dockerfile + same source code, built twice → produces two images with identical layer hashes (Docker recognizes no change occurred, near-instant "build" due to caching).
  • Same Dockerfile + different source code/args each build → each build produces a genuinely new image with a new content hash, even under the same tag name (old tag reference simply moves to the new image).

7.2 Multi-Stage Builds — Multiple "Images" in One Dockerfile

A single Dockerfile can define multiple named FROM ... AS stageName stages. Each stage technically builds its own intermediate image, but only the final stage becomes the image you actually ship — earlier stages (compilers, build tools) are discarded, keeping the shipped image small and secure.
FROM node:20 AS build          # Stage 1 — has Node, npm, dev dependencies (large)
...
FROM nginx:alpine AS final      # Stage 2 — final shipped image (small, no Node at all)
COPY --from=build /app/dist /usr/share/nginx/html
  • You can even build and tag intermediate stages separately for debugging: docker build --target build -t order-service:build-debug .
  • Real orgs commonly keep 3 tags per release: the immutable <build-number> tag, a semantic version tag like 1.4.2, and a moving latest/stable tag.

7.3 Tagging Strategy Used in Real Organizations

Tag StyleExamplePurpose
Build numberorder-service:482Immutable, traceable to exact CI/CD pipeline run
Git SHAorder-service:a1b2c3dTraceable to exact commit, useful for debugging "what code is actually running"
Semantic versionorder-service:2.3.0Human-readable release version, follows semver
Environment moving tagorder-service:qa-latestAlways points to whatever is currently deployed in QA
latestorder-service:latestAvoid relying on this in production — ambiguous, not reproducible
Interview tip: Never deploy production using the latest tag — it's a moving target and you can't be 100% sure which exact build is running. Always deploy an immutable tag (build number or git SHA).

8. Dockerfile for Spring Boot — Full Real Example

8.1 Project Structure

order-service/
├── src/main/java/...
├── src/main/resources/application.yml
├── pom.xml
├── Dockerfile
└── .dockerignore

8.2 Production-Grade Multi-Stage Dockerfile

FROM maven:3.9-eclipse-temurin-17 AS build
WORKDIR /app
COPY pom.xml .
RUN mvn dependency:go-offline -B
COPY src ./src
RUN mvn clean package -DskipTests -B

FROM eclipse-temurin:17-jre-alpine
RUN addgroup -S spring && adduser -S spring -G spring
WORKDIR /app
COPY --from=build /app/target/order-service-*.jar app.jar
RUN chown spring:spring app.jar
USER spring
EXPOSE 8080
HEALTHCHECK --interval=30s --timeout=3s --retries=3 \
  CMD wget -qO- http://localhost:8080/actuator/health | grep UP || exit 1
ENTRYPOINT ["java", "-XX:+UseContainerSupport", "-XX:MaxRAMPercentage=75.0", "-jar", "app.jar"]
Why -XX:+UseContainerSupport and MaxRAMPercentage? Without these JVM flags, older JVMs could misread the host's total memory instead of the container's cgroup memory limit, causing OOM-killed containers even when heap usage looked "fine" from the JVM's own perspective. Modern JDKs (10+) detect cgroup limits automatically, but explicitly setting MaxRAMPercentage is still a common real-world safeguard.

8.3 Building & Running It

docker build -t order-service:1.0.0 .
docker run -d -p 8080:8080 --name order-service \
  -e SPRING_PROFILES_ACTIVE=prod \
  -e DB_URL=jdbc:postgresql://prod-db:5432/orders \
  order-service:1.0.0

9. Dockerfile for React — Full Real Example (Multi-Stage with Nginx)

9.1 Project Structure

customer-portal/
├── src/
├── public/
├── package.json
├── .env.production
├── Dockerfile
├── nginx.conf
└── .dockerignore

9.2 Multi-Stage Dockerfile

# Stage 1: Build the static bundle
FROM node:20-alpine AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci                                 # reproducible install using the lock file
COPY . .
RUN npm run build                          # produces /app/build (or /dist for Vite)

# Stage 2: Serve with Nginx — tiny final image, no Node.js at all
FROM nginx:1.27-alpine
COPY --from=build /app/build /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE 80
HEALTHCHECK --interval=30s CMD wget -qO- http://localhost:80 || exit 1
CMD ["nginx", "-g", "daemon off;"]

9.3 nginx.conf (Handles React Router + API Proxy)

server {
    listen 80;
    root /usr/share/nginx/html;
    index index.html;

    location / {
        try_files $uri /index.html;      # React Router — always fall back to index.html
    }

    location /api/ {
        proxy_pass http://order-service:8080/;  # proxy calls to backend service inside the cluster
    }
}

9.4 Environment Config for React (Build-Time vs Runtime)

React environment variables (REACT_APP_* / Vite's VITE_*) are baked into the static bundle at build time — they cannot be changed after the image is built like a backend env var can. Real orgs solve this by either (a) building one image per environment, or (b) injecting a small env-config.js file at container startup that the app reads at runtime.
# Runtime-injectable config approach — entrypoint script generates env-config.js from container env vars
#!/bin/sh
echo "window._env_ = { API_URL: \"$API_URL\" };" > /usr/share/nginx/html/env-config.js
exec nginx -g 'daemon off;'

9.5 Building & Running It

docker build -t customer-portal:1.0.0 .
docker run -d -p 80:80 --name customer-portal customer-portal:1.0.0

10. Docker Compose — Running Microservices Together

10.1 Why Compose Exists

A real application is rarely one container — it's a Spring Boot backend + a Postgres database + Redis cache + a React frontend, all needing to talk to each other. Docker Compose lets you define this whole multi-container stack in one YAML file and start it with a single command — perfect for local development and demos.

10.2 Real docker-compose.yml — Microservices Example

version: "3.9"
services:
  order-service:
    build: ./order-service
    image: order-service:local
    ports: [ "8080:8080" ]
    environment:
      SPRING_PROFILES_ACTIVE: dev
      DB_URL: jdbc:postgresql://postgres:5432/orders
    depends_on:
      postgres: { condition: service_healthy }
    networks: [ backend-net ]

  customer-portal:
    build: ./customer-portal
    image: customer-portal:local
    ports: [ "80:80" ]
    depends_on: [ order-service ]
    networks: [ backend-net ]

  postgres:
    image: postgres:15-alpine
    environment:
      POSTGRES_DB: orders
      POSTGRES_PASSWORD: devpass
    volumes: [ "pgdata:/var/lib/postgresql/data" ]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      retries: 5
    networks: [ backend-net ]

  redis:
    image: redis:7-alpine
    networks: [ backend-net ]

volumes:
  pgdata:

networks:
  backend-net:

10.3 Key Commands

docker compose up -d          # builds (if needed) and starts the whole stack in background
docker compose logs -f order-service   # tail logs of one service
docker compose down           # stops and removes containers/networks (add -v to also remove volumes)
docker compose ps             # status of all services in the stack
Real scenario: "New developers onboarding to our team run docker compose up once and get the full backend + database + cache + frontend running locally in under 2 minutes — no manual Postgres install, no version mismatch, no 20-step setup doc."

12.4 Real-Time Debugging Scenario Using Commands

Real scenario: "Container keeps restarting" — first docker ps -a to see exit code, then docker logs container_id to see the crash reason, then docker inspect container_id to check memory limits (an exit code 137 usually means OOM-killed), then reproduce interactively with docker run -it --entrypoint sh image to poke around before the crash-looping entrypoint runs.

13. Docker Security — Before Docker vs After Docker

13.1 Security Before Docker (VM/Physical Era)

  • Isolation was at the OS/hypervisor level — strong, but coarse-grained (one whole VM per workload).
  • Patch management meant patching whole guest OS images per VM — slow, inconsistent across teams.
  • Attack surface = entire OS + all installed packages, even ones the app didn't need.
  • Secrets were often placed in server-level config files or environment scripts, sometimes checked into shared file shares.

13.2 Security Concerns Docker Introduced

Because containers share the host kernel, a container escape vulnerability is more impactful than a VM escape (rarer, but the blast radius includes the whole host). Also, most base images historically defaulted to running as root inside the container, which is risky if an app is compromised.

13.3 Docker Security Best Practices (After Docker, Done Right)

PracticeWhy
Run as non-root (USER app)Limits what an attacker can do if the app process is compromised
Use minimal base images (Alpine/Distroless)Smaller attack surface — fewer packages, fewer CVEs
Multi-stage buildsBuild tools/compilers never ship in the final image
Scan images (Trivy, Snyk, Docker Scout, ACR/ECR built-in scanning)Finds known CVEs in base image + dependencies before deployment

16. Introduction to Kubernetes — Why We Needed It After Docker

16.1 The Problem Docker Alone Doesn't Solve

Docker is excellent at packaging and running one container on one host. But real organizations run hundreds of containers across many hosts, and need answers to: What happens when a container crashes? How do we scale to 10 replicas during peak traffic? How do containers on different hosts find each other? How do we roll out updates without downtime? Docker alone doesn't answer these — that's what Kubernetes (K8s) (originally built by Google, based on their internal "Borg" system) was built for.

16.2 What Kubernetes Actually Does

NeedWhat Kubernetes Provides
Container crashesAutomatically restarts it (self-healing)
Traffic spikesHorizontal Pod Autoscaler adds more replicas automatically
Multi-host networkingBuilt-in cluster networking so pods find each other by name regardless of which node they're on
Zero-downtime updatesRolling updates, readiness probes control when new pods receive traffic
Node failureReschedules pods from a dead node onto healthy nodes automatically
Config/secret management at scaleConfigMaps and Secrets decoupled from container images
Declarative infrastructureYou describe the desired state (YAML); Kubernetes continuously works to match reality to it

16.3 Kubernetes vs Plain Docker — Side by Side

Docker Alone vs Docker + Kubernetes
Docker alone: you manually run/restart/scale containers on each host
— vs —
Kubernetes: you declare "I want 4 replicas of order-service, always healthy" — K8s makes it true, continuously
Interview one-liner: "Docker packages and runs a single container; Kubernetes orchestrates many containers across many machines — handling scheduling, scaling, networking, self-healing, and rollouts automatically based on a declared desired state."

17.4 The Reconciliation Loop (Core Kubernetes Philosophy)

Every controller in Kubernetes follows the same pattern: Observe current state → Compare to desired state (your YAML) → Act to close the gap → repeat forever. This is why deleting a pod managed by a Deployment doesn't actually remove it for long — the ReplicaSet controller immediately notices "3 desired, 2 actual" and creates a replacement.

18.2 Pod

The smallest deployable unit in Kubernetes — one or more tightly coupled containers that share network/storage (usually just 1 container per pod for microservices, e.g., one Spring Boot container).

18.3 ReplicaSet

Ensures a specified number of identical pod replicas are running at all times — replaces a crashed pod automatically. You rarely create these directly; Deployments manage them for you.

18.4 Deployment

The object you actually work with day-to-day. Manages ReplicaSets, handles rolling updates/rollbacks, and describes the desired state of your application (image version, replica count, resource limits, probes).

18.5 Service

Gives a stable network identity (a DNS name and virtual IP) to a set of pods, even as individual pods are replaced. Types: ClusterIP (internal only, default), NodePort (exposes on each node's IP), LoadBalancer (provisions a cloud load balancer, e.g., Azure Load Balancer).

18.6 Ingress

Manages external HTTP/HTTPS access into the cluster, with host/path-based routing and TLS termination — usually backed by an Ingress Controller like NGINX Ingress or Azure Application Gateway Ingress Controller (AGIC).

18.7 StatefulSet & DaemonSet (Good to Know)

ObjectUse Case
StatefulSetFor stateful apps needing stable network identity and storage per replica (e.g., a Kafka broker, self-managed database)
DaemonSetEnsures one pod runs on every (or selected) node — used for log collectors, monitoring agents
Job / CronJobRun-to-completion batch tasks, or scheduled recurring tasks (e.g., nightly report generation)

19. ConfigMaps, Secrets, Namespaces Explained

19.1 ConfigMap

Stores non-sensitive configuration (URLs, feature flags, log levels) separately from the container image, so the same image can run in Dev/QA/Prod with different config injected as env vars or mounted files.
apiVersion: v1
kind: ConfigMap
metadata: { name: order-service-config, namespace: prod }
data:
  LOG_LEVEL: "INFO"
  FEATURE_NEW_CHECKOUT: "true"

19.2 Secret

Same idea as ConfigMap but intended for sensitive values — base64-encoded at rest by default (not encrypted unless you enable encryption-at-rest or use an external secrets provider like Azure Key Vault via CSI driver).
apiVersion: v1
kind: Secret
metadata: { name: order-service-secrets, namespace: prod }
type: Opaque
data:
  DB_PASSWORD: cGFzc3dvcmQxMjM=   # base64 encoded — NOT encryption, just encoding
Base64 is not encryption — anyone with API access can decode it instantly. Real organizations integrate an external secret manager (Azure Key Vault Provider for Secrets Store CSI Driver, HashiCorp Vault) so actual secret values never sit in etcd in a reversible format, and enable etcd encryption-at-rest as a baseline.

19.3 Namespaces — Logical Isolation

A Namespace partitions one physical cluster into multiple virtual clusters — commonly one per environment (dev, qa, staging, prod) or per team, with its own resource quotas and RBAC rules.
kubectl create namespace dev
kubectl get pods -n prod
kubectl config set-context --current --namespace=dev   # switch default namespace for convenience
NamespaceTypical Use
kube-systemKubernetes' own control components (DNS, kube-proxy, etc.) — don't touch
dev / qa / staging / prodOne cluster shared across environments, isolated logically (common cost-saving pattern for non-prod)
monitoringPrometheus, Grafana, Alertmanager stack

23. Kubernetes Autoscaling & Self-Healing

23.1 Self-Healing Mechanisms

FailureHow K8s Self-Heals
Container crasheskubelet restarts it per the pod's restart policy
Pod fails readiness probeRemoved from Service load-balancing until it passes again — no traffic sent to unhealthy pods
Pod fails liveness probe repeatedlyKubelet kills and restarts the container
Node goes downController Manager notices missed heartbeats, reschedules its pods onto healthy nodes
Fewer pods than desired replicasReplicaSet controller creates new pods immediately

23.2 Horizontal Pod Autoscaler (HPA)

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: order-service-hpa, namespace: prod }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: order-service }
  minReplicas: 4
  maxReplicas: 20
  metrics:
  - type: Resource
    resource:
      name: cpu
      target: { type: Utilization, averageUtilization: 70 }
HPA watches a metric (CPU by default, or custom metrics via Prometheus Adapter — e.g., queue length, requests/sec) and automatically adds/removes pod replicas to keep it near the target.

23.3 Cluster Autoscaler / Node Autoscaling

While HPA scales pods, the Cluster Autoscaler (or AKS's built-in node autoscaling) scales the actual number of worker nodes — if pods can't be scheduled due to insufficient node capacity, it provisions new VM nodes automatically, and scales down idle nodes to save cost.

23.4 Vertical Pod Autoscaler (VPA)

Instead of adding more pod replicas, VPA adjusts the CPU/memory requests/limits of existing pods based on observed usage — less commonly used in production for latency-sensitive apps since it requires pod restarts to apply new resource values.

24. Kubernetes Security — Before K8s vs After K8s

24.1 Security Before Kubernetes (Plain Docker on Servers)

  • No standard RBAC across many hosts — access control was per-server SSH keys/users.
  • No built-in network policy — any container could often reach any other container/service on the host network.
  • Secrets scattered across server config files, scripts, and shared drives.
  • Manual, inconsistent patching per host.

24.2 What Kubernetes Adds for Security

FeaturePurpose
RBAC (Role-Based Access Control)Fine-grained control over who can do what, per namespace/resource (e.g., QA team can only view pods in the qa namespace)
Network PoliciesFirewall-like rules restricting which pods can talk to which — default is "all pods can talk to all pods" unless policies are applied
Pod Security Standards / Admission ControllersBlocks pods from running as root, using host networking, or mounting sensitive host paths, unless explicitly allowed
Secrets + external secret providersCentralizes and (with add-ons) encrypts sensitive config, integrates with Key Vault/Vault
Service AccountsIdentity for pods/apps to authenticate to the Kubernetes API or cloud services (e.g., AKS pod identity/workload identity to access Azure resources without embedded credentials)
Image Pull Secrets + private registriesEnsures only authorized images from trusted registries can be deployed
etcd encryption at restProtects the cluster's own state store (which contains Secrets) from disk-level exposure

24.3 Example RBAC Role (Real Pattern)

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: { namespace: qa, name: qa-read-only }
rules:
- apiGroups: [""]
  resources: ["pods", "services", "deployments"]
  verbs: ["get", "list", "watch"]     # read-only — QA team can view but not modify
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata: { name: qa-team-binding, namespace: qa }
subjects:
- kind: Group
  name: "qa-team"
roleRef: { kind: Role, name: qa-read-only, apiGroup: rbac.authorization.k8s.io }

24.4 Example Network Policy (Zero-Trust Style)

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: order-service-allow, namespace: prod }
spec:
  podSelector: { matchLabels: { app: order-service } }
  policyTypes: [ Ingress ]
  ingress:
  - from:
    - podSelector: { matchLabels: { app: customer-portal } }   # only frontend can call order-service
    ports: [{ port: 8080 }]
Interview tip: By default, Kubernetes networking is "flat" — any pod can reach any other pod. Network Policies let you move to a zero-trust model where services must be explicitly allowed to talk to each other, drastically reducing lateral movement if one service is compromised.

26.2 Service-to-Service Communication Patterns

  • Service Mesh (Istio/Linkerd): adds mTLS between services, fine-grained traffic splitting (for Canary), and detailed service-to-service observability without changing app code.

26.3 Helm — Packaging Microservices for Kubernetes

Helm is the de-facto package manager for Kubernetes — a "Helm chart" templates your YAML (Deployment/Service/Ingress/ConfigMap) so the same chart can be reused across order-service, payment-service, etc., with only values (image tag, replica count, resource limits) differing per service/environment via a values.yaml file.
helm install order-service ./charts/microservice -f values-prod.yaml -n prod
helm upgrade order-service ./charts/microservice --set image.tag=483 -n prod
helm rollback order-service 1 -n prod

  1. Developer writes Spring Boot/React code locally, tests using docker compose up against local Postgres/Redis containers.

30. Interview Questions & Answers (Basic → Advanced → Scenario Based)

Q1. Why did Docker replace/reduce reliance on Virtual Machines?
Docker containers share the host OS kernel instead of bundling a full guest OS per workload, making them far lighter (MBs vs GBs), faster to start (seconds vs minutes), and more portable — the same image runs identically on any host with a compatible container runtime.
Q2. What is the difference between an image and a container?
An image is an immutable, read-only build template made of layers. A container is a running (or stopped) instance of that image with an added writable layer for runtime changes. One image can produce many running containers.
Q3. Explain multi-stage Docker builds and why they matter.
Multi-stage builds let you use one Dockerfile with several FROM ... AS stage blocks — a heavy "build" stage compiles the app, and a minimal "runtime" stage copies only the final artifact. This keeps the shipped image small and avoids bundling compilers/build tools that increase size and attack surface.
Q4. How many images can one Dockerfile produce?
Unlimited — a Dockerfile is just a recipe. Every docker build run (with different tags, build args, or source code state) produces a distinct image. Real orgs commonly tag by build number, git SHA, and semantic version for the same underlying Dockerfile.
Q5. What's the difference between CMD and ENTRYPOINT?
ENTRYPOINT defines the fixed command that always runs and is hard to override; CMD provides default arguments that can be easily overridden at docker run. The common real-world pattern combines both — ENTRYPOINT for the binary, CMD for overridable default args.
Q6. How do you keep Docker images secure?
Use minimal base images (Alpine/Distroless), run as a non-root user, use multi-stage builds so build tools don't ship, scan images for CVEs (Trivy/Snyk) in the pipeline, never bake secrets into layers, and pull only from trusted private registries.
Q7. Why do we need Kubernetes if we already have Docker?
Docker runs a single container on a single host well, but doesn't handle multi-host scheduling, automatic scaling, self-healing after crashes/node failures, zero-downtime rollouts, or service discovery across many machines — Kubernetes orchestrates all of that declaratively.
Q8. Explain the relationship between Pod, ReplicaSet, and Deployment.
A Pod is the smallest deployable unit (one or more containers). A ReplicaSet ensures a set number of identical Pods are always running. A Deployment manages ReplicaSets and adds rollout/rollback strategy on top — in practice, you almost always work with Deployments directly.
Q9. What's the difference between a readiness probe and a liveness probe?
A readiness probe determines if a pod is ready to receive traffic — if it fails, the pod is removed from the Service's endpoints but not restarted. A liveness probe determines if a pod is alive at all — if it fails repeatedly, kubelet kills and restarts the container.
Real scenario: A Spring Boot service that's still warming up its cache on startup should fail readiness (so it gets no traffic yet) without failing liveness (so it isn't needlessly restarted while legitimately starting up).
Q10. How does a rolling update actually achieve zero downtime?
The Deployment creates new pods gradually (controlled by maxSurge) while removing old pods gradually (controlled by maxUnavailable), and only routes traffic to new pods once they pass their readiness probe — so there's always a sufficient number of healthy pods serving traffic throughout the rollout.
Q11. What tools do you use for monitoring pods in production, and why more than one?
Rancher for multi-cluster management/RBAC visibility, Prometheus + Grafana for metrics and dashboards, Loki/EFK for centralized logs, and Alertmanager for on-call alerting. Each tool covers a different observability pillar (management, metrics, logs, alerts) — no single tool covers all of them well.
Q12. How do Secrets differ from ConfigMaps, and are Kubernetes Secrets actually secure by default?
ConfigMaps hold non-sensitive config; Secrets hold sensitive values but are only base64-encoded by default — not encrypted. Real production setups add etcd encryption-at-rest and/or integrate an external secret manager like Azure Key Vault via the Secrets Store CSI Driver for genuine encryption and centralized rotation.
Q13. A pod is stuck in CrashLoopBackOff — walk through your debugging steps.
First kubectl describe pod to see recent events and exit code; then kubectl logs --previous to see the crash's actual error output; check for missing/incorrect ConfigMap or Secret values, a misconfigured health check path, or an unreachable dependency (DB/downstream service); fix and reapply, watching kubectl rollout status.
Q14. How would you roll back a bad production deployment in Kubernetes?
kubectl rollout undo deployment/order-service -n prod instantly reverts to the previous ReplicaSet revision — no rebuild needed since the previous image is still in the registry and the previous ReplicaSet spec is retained in rollout history.
Q15. How does Kubernetes autoscaling work end to end during a traffic spike?
The Horizontal Pod Autoscaler watches a metric (e.g., CPU utilization) and increases pod replicas when it exceeds the target. If the cluster's existing nodes can't fit the new pods, the Cluster Autoscaler (or AKS node autoscaling) provisions additional worker nodes automatically, and scales back down once demand drops.
Q16. How do you integrate Docker/Kubernetes into an Azure DevOps pipeline?
A Docker@2 task builds and pushes the image to Azure Container Registry using a Service Connection; a subsequent deployment job targeting a Kubernetes-backed Environment (with approval gates) uses the KubernetesManifest@1 task with an AKS Service Connection to apply the Deployment/Service/Ingress manifests, substituting the new image tag.
Q17. What real-world issue have you faced with Docker/Kubernetes and how did you fix it?
Example: a Spring Boot service was repeatedly OOMKilled in production despite "normal-looking" heap usage — root cause was the JVM not respecting the container's cgroup memory limit on an older JDK image. Fixed by upgrading the base image and explicitly setting -XX:MaxRAMPercentage, aligned with the pod's configured memory limit.
Q18. What is the difference between a Service and an Ingress?
A Service provides a stable internal (or basic external via LoadBalancer/NodePort) network endpoint for a set of pods. An Ingress sits in front of Services and handles external HTTP/HTTPS routing by host/path plus TLS termination, typically via a single shared Ingress Controller for the whole cluster instead of one LoadBalancer per service.
Q19. How do microservices communicate on Kubernetes, and what's the tradeoff between sync and async calls?
Synchronous REST/gRPC calls via Service DNS names are simple but couple the caller's availability to the callee's uptime. Asynchronous messaging (Kafka/RabbitMQ) decouples services — the publisher doesn't wait on the consumer — improving resilience at the cost of added infrastructure and eventual-consistency complexity.
Q20. What's the difference between Docker Swarm and Kubernetes?
Both orchestrate containers, but Kubernetes has a far larger ecosystem, more granular objects (ConfigMaps, RBAC, NetworkPolicies, CRDs), and is the de-facto industry standard; Swarm is simpler to set up but has largely fallen out of favor in real organizations compared to Kubernetes (especially managed offerings like AKS/EKS/GKE).

31. Final Summary & Cheat Sheet

Before Docker: physical servers and VMs were heavy, slow to provision, and caused "works on my machine" inconsistency between Dev/QA/Prod.

After Docker: apps are packaged with their exact dependencies into small, fast, portable images that run identically everywhere.

Before Kubernetes: running many containers across many hosts required manual scaling, manual restarts, and manual networking glue.

After Kubernetes: you declare desired state (replica count, resources, health checks) and the cluster continuously self-heals, scales, and rolls out updates with zero downtime.

Our real Azure setup: Azure Repos → Azure Pipelines (build, test, Trivy scan) → Azure Container Registry → Azure Kubernetes Service, with approval gates on Staging/Production Environments, secrets from Azure Key Vault, and monitoring via Azure Monitor/Prometheus/Grafana.
